# Architecture

Castle Doom 3 reads Doom 3 (id Tech 4) data at runtime and turns it into Castle Game Engine (CGE) scenes. Nothing is converted offline.

```
 PK4 / loose files ──► Doom3Files (d3fs:) ──┬─► Doom3Lexer ─► Doom3Decls (materials, entityDefs, models, skins, sounds)
                                            │                    │
                                            │                    ├─► Doom3Images (d3img:, image programs)
                                            │                    └─► Doom3Materials (X3D appearances)
                                            ├─► Doom3Proc   (.proc areas, brush models, portals, BSP)
                                            ├─► Doom3MapFile (.map entities)
                                            ├─► Doom3Md5    (.md5mesh / .md5anim, CPU skinning)
                                            ├─► Doom3StaticModels (.lwo / .ase)
                                            ├─► Doom3Collision (.cm)
                                            └─► Doom3Portals (portal visibility)
                                                         │
                                       Doom3Level (TDoom3Map component) ─► Doom3World (TD3Game: doors, AI, sounds, player)
                                                         │
                                         GameViewPlay / GameViewMenu, Doom3Hud, Doom3Console
```

## Units

| Unit | Role |
|---|---|
| `Doom3Files` | Virtual file system. Reads each PK4's ZIP central directory once, indexes paths (lowercase, `/`), inflates entries on demand from a `TFileStream`, so 300 MB+ paks are never loaded whole. Loose directories override PK4s. Registers `d3fs:`. |
| `Doom3Lexer` | idLexer subset shared by all text formats: quoted strings, punctuation, `//` and `/* */` comments, paths as single tokens, locale-independent numbers, `SkipBracedSection`. |
| `Doom3Decls` | Scans `materials/*.mtr`, `def/*.def`, `skins/*.skin`, `sound/*.sndshd` and indexes every declaration body by type and name (first definition wins, like Doom 3). Bodies are parsed on demand into `TD3Material`, `TD3ModelDecl`, `TD3Skin`, `TD3SoundShader` and merged entityDef dictionaries (`inherit`). Undeclared materials become implicit ones named after their image. |
| `Doom3Images` | Finds image files (`.tga`, `.png`, `.jpg`, `dds/*.dds`) and evaluates image programs. Normal maps are served as `d3img:/normal/<program>`: plain Doom 3 normal maps get their green channel flipped, `heightmap(img, scale)` becomes a normal map, `addnormals(a, b)` adds slopes. Output is uncompressed TGA. |
| `Doom3Materials` | `TD3Material` → `TAppearanceNode`: Phong material with diffuse, normal and specular textures (shininess 16/128, Doom 3's exponent), alpha test → `amMask`, translucent → `amBlend`; blended stages → unlit material with `TBlendModeNode` (`add` = one/one, `filter` = dst_color/zero). |
| `Doom3Proc` | `mapProcFile003`: models with surfaces (`( x y z s t nx ny nz )` vertexes, indexes), `interAreaPortals`, `nodes` (area BSP, `PointInArea`). Shadow models are skipped. |
| `Doom3MapFile` | `.map` entities (key / value pairs, primitive count; brushes and patches skipped), `origin` / `angle` / `rotation` helpers, coordinate conversion. |
| `Doom3Md5` | md5mesh joints / meshes / weights, md5anim hierarchy / baseframe / frames, absolute poses, frame interpolation (lerp + normalized quaternion lerp), skinning. `TD3Md5Instance` owns a `TCastleScene`, `PlayAnim`, `Update`. `Md5Cache` shares parsed files. |
| `Doom3StaticModels` | LWO2 (`TAGS`, `LAYR`, `PNTS`, `VMAP` / `VMAD` `TXUV`, `POLS` `FACE` as triangle fans, `PTAG` `SURF`) and ASE (`*MATERIAL` / `*SUBMATERIAL` `*BITMAP` and UV tiling / offset, `*GEOMOBJECT` meshes, `*MESH_MTLID`, `*MATERIAL_REF`). Surfaces per material with Doom-style smooth normals (vertexes sharing position and UV). `StaticModels` caches them. |
| `Doom3Collision` | `.cm` files: per `collisionModel` the vertices, edges (edge 0 is a dummy; a negative edge in a polygon is used backwards and starts at its second vertex), BSP nodes (counted), polygons (`numEdges ( edges ) ( normal ) dist ( min ) ( max ) "material"`) and brushes (`n { ( normal ) dist ... } ( min ) ( max ) "contents"`). `PlayerTriangles` / `BuildCollisionNode` turn the polygons whose material `BlocksPlayer` into triangle fans. |
| `Doom3Expressions` | Material expressions as trees (`TD3Expr.Eval`, `IsConstant`, `UsesTime`) parsed with Doom 3's operator priorities, and `TD3Table` (`snap`, `clamp`, the first value copied to the end, lookups like `idDeclTable::TableLookup`). |
| `Doom3LightEffects` | Doom 3 light volumes: `PointLightMatrix` / `ProjectedLightMatrix` (CGE world -> the light's texture space `(s w, t w, q, w)`), `LightTexCoord`, `CreateLightEffect` (per-light GLSL with a uniquely named matrix uniform), `LightLibraryEffect` / `AddLightLibrary`, `ProjectionShape`. |
| `Doom3Portals` | `TD3PortalVisibility`: the portals in CGE coordinates, per area portal lists, `Compute` (portal flow with polygon clipping and per-portal narrowing, closed portals), `AreasWithinRadius` (areas a light reaches), `PortalsInBox` (portals a door closes), `ClipPolygon`. |
| `Doom3Gui` | `.gui` files: `TD3Gui` / `TD3GuiWindow` (windowDef, editDef, choiceDef... trees; properties as comma-separated tokens; events and variable declarations skipped), `RenderGui` (software rendering), `GuiImageUrl` (cache per path and state, `d3gui:` protocol), `GuiSurfaceUrl` / `GuiSurfPath` (guisurf keywords). |
| `Doom3Camera` | `.md5camera` camera anims: `TD3CameraAnim` (frames, cuts, `Sample` at a time). |
| `Doom3Script` | Doom 3 scripts: `TD3ScriptVM` compiles the whole program (preprocessor, idCompiler's grammar and operator priorities, objects) to a stack machine and runs its threads; events other than the threads' own go to a `TD3ScriptHost`. |
| `Doom3Level` | `TDoom3Map` (`TCastleTransform`, registered for the editor): builds the area scenes, lights, brush entities and md5 entities of a map. |
| `Doom3World` | `TD3Game`: movers (`func_door`, `func_rotating`), speakers, monsters, triggers and entity activation, player health / armor, pistol, use. |
| `Doom3Hud`, `Doom3Console` | UI components drawn with `DrawRectangle` and `UIFont`. |
| `GameViewPlay`, `GameViewMenu`, `GameInitialize` | Views, input, demo-script harness, data source setup and command line. |

## Coordinates and conventions

- Doom 3 is X forward, Y left, Z up; CGE is Y up. `D3ToCge(v) = (v.x, v.z, -v.y)`, a proper rotation, so triangle winding is preserved. 1 unit = 1 Doom 3 unit (an inch): player eye height 68, radius 16, speeds 140 / 220, gravity on.
- Doom 3 front faces are clockwise (its face plane is `(v2 - v0) × (v1 - v0)`), so geometry sets `Ccw := False`; `twoSided` materials set `Solid := False`.
- Doom 3's `t` texture coordinate goes down the image, CGE images are bottom-to-top: `v = 1 - t`. Because of this flip, the tangent-space bitangent points the other way, hence the green flip of normal maps.
- md5 quaternions store x, y, z; w is `-sqrt(1 - x² - y² - z²)`. Joint poses are made absolute by `parent.q * local.q` and `parent.pos + parent.q.rotate(local.pos)`.
- Entity rotation: idMat3 rows are the rotated local axes (`world = x·row0 + y·row1 + z·row2`). `D3RotateCge` applies it to CGE vectors; `SetD3Rotation` orients a transform with it. CGE's default `TCastleTransform.Orientation` is `otUpYDirectionZ` (direction = local **+Z**), which `SetD3Rotation` respects; a unit test checks that yaw 135 turns a model's +X to (cos 135, sin 135).
- Static models: LightWave points are read as Doom 3 `(x, z, y)` (a mirror), so LWO polygons are counter-clockwise from the front in Doom 3 space; Doom 3 flips ASE faces (A, C, B) to its clockwise style, so ASE files are counter-clockwise too. Both use `Ccw := True`. Doom 3's `t = 1 - v`, so CGE uses the files' `v` directly. ASE materials are the `*BITMAP` path from `base/` on, without the extension.
- A light's CGE radius is twice its Doom 3 light box, with quadratic attenuation `1 / (1 + 8 d² / r²)`: 1/3 at the box, ~3% where CGE cuts the light off (CGE stops a light hard at its radius).
- Sound shader distances are meters (× 39.37 units); volume is dB.

## Collision

- With a `maps/<name>.cm` (and `UseCollisionModel`), `TDoom3Map` loads the `worldMap` model into `WorldCollision`: invisible (`Visible := False`), `PreciseCollisions`, not pickable. The area scenes then have `Collides := False`. So the player and `WorldSegmentCollision` (monster sight, monster movement) use Doom 3's collision geometry with its `playerclip` brushes and without render-only detail, while `WorldRayCast` (shots, monster floor following) hits what you see.
- Contents come from the polygon's material, like Doom 3's surface parameters: `playerclip` blocks the player only; `monsterclip`, `nonsolid`, `water`, `trigger`, `ikclip`, `aassolid`... clear solid (`TD3Material.BlocksPlayer`).
- Brush entities (doors, movers) keep colliding with their render geometry, which moves with them; their `.cm` models are parsed but not used yet. Without a `.cm`, the render geometry collides as before.

## Light volumes

- Doom 3 lights don't fade with distance: a lit point is mapped into the light's texture space (`R_DeriveLightData`'s `lightProject`) and lit only inside 0..1. Point lights are boxes (`light_radius` around the origin, rotated by `rotation`; `light_center` only moves where the light comes from); projected lights are pyramids from the origin along `light_target`, `light_right` / `light_up` being half the width / height at the target, the falloff running from `light_start` to `light_end` (or the target).
- `TDoom3Map.BuildLights` makes every light a `TPointLightNode` without attenuation whose `Radius` only bounds CGE's per-shape light lists (the box's corner, the frustum), with an `Effect` from `CreateLightEffect`. The GLSL plugs `PLUG_light_scale`: `p = d3_light_matrix_N * (castle_CameraInverseMatrix * castle_vertex_eye)` gives the fragment's light coordinates; outside the volume the light adds nothing, inside it is scaled by the projection and falloff shapes.
- `castle_vertex_eye` is the Phong shader's varying (CGE's default shading is Phong, so light code runs per fragment) and `castle_CameraInverseMatrix` comes from CGE's `castle-shader:/EyeWorldSpace.glsl` library. Light effects can't enable libraries, appearance / group effects can: every scene the map builds (areas, brush entities, static and md5 models) gets `AddLightLibrary` on its root, otherwise the matrix is zero and map lights add nothing to it.
- Projection and falloff **images** are approximated analytically: textures referenced only by light effects are not bound by CGE's renderer (they read as black / garbage). `ProjectionShape` picks a center-bright soft square for `square*` images, a full volume for `bright` / `white`, otherwise a soft disc; the depth falloff follows Doom 3's default point / projected falloff images.
- Uniform names must be unique per light (several lights' code ends up in one shader), so they are suffixed with the light's index.
- `r_lightVolumes 0` (`Doom3LightEffects.LightVolumes`) reloads the map with plain spheres / X3D spot lights for comparison.

## GUIs

- A material with `guisurf entity` (`entity2`, `entity3`) shows the GUI named by its entity's `gui` (`gui2`, `gui3`) key; `guisurf guis/x.gui` names it directly. `TDoom3Map.BuildProcModel` (brush entities pass their entity) and `TD3StaticModel.BuildNode` (static models pass the entity's keys) give such surfaces `GuiAppearance`: unlit, opaque, the GUI image as emissive texture, using the surface's own texture coordinates (Doom 3 maps the 640 x 480 GUI onto them).
- `RenderGui` draws the window tree in software, so it needs no OpenGL and unit tests can check pixels: background colors, a background material's image (scaled, tinted by `matcolor`), borders, and word-wrapped text with CGE's built-in UI font (`CastleTextureFont_DefaultUi`): every glyph is scaled from the font atlas (Doom 3 fonts are 48 pixels at `textscale 1`) and placed like CGE does, at `pen x - G.X`, `baseline - G.Y`. `gui::name` texts read the GUI state: the entity's keys.
- Properties are read as tokens separated by commas (`rect 0, 0, 640, 480`), so one-line `windowDef x { rect ... backcolor ... }` blocks work; `definevec4` / `float`... declarations have a name before the value.
- Images are cached per GUI path and `gui_*` state and served as `d3gui:/guiN.tga` (TGA), so CGE's texture cache shares them. Not yet: events and scripts (`onTime` transitions, `onAction`), the cursor and interaction, Doom 3's fonts, `rotate` / `shear`.

## Material stages

- `TD3Material` keeps the texture matrix keywords of its diffuse stage (`DiffuseTexOps`) and of its first plain stage (`StageTexOps`): `scroll` / `translate`, `scale`, `centerScale`, `shear`, `rotate` (in cycles, around the texture center), each with expressions. `TexMatrix` composes them like idMaterial's `MultiplyTextureMatrix` (a new keyword applies after the previous ones) and converts to CGE's texture coordinates (`v = 1 - t`: `F M F` with `F (s, v) = (s, 1 - v)`), as a 4x4 matrix for a `TextureTransformMatrix3D` node.
- `MaterialAppearance` adds that node to the appearance (the diffuse stage's matrix applies to the normal and specular maps too) and sets the plain stage's color registers on the unlit material (`EmissiveColor`, and `Transparency` for `blend blend` stages). Appearances that change with time (`UsesTime`) are registered; `TDoom3Map.Update` calls `UpdateAnimatedSurfaces(Time)` every frame and `ClearMap` forgets them. World surfaces use shader parameters 1.
- More stages: plain stages after the first one are kept in `TD3Material.ExtraStages` (image, blend, color registers, texture matrix, alpha test). `OverlayCount` stages are drawn over the base appearance: for lit materials the first plain stage too, otherwise only the extra ones. `BuildProcModel` and static models add one shape per overlay, a copy of the surface moved `OverlayOffset` (0.25 units, more for each next overlay) along the vertex normals with `OverlayAppearance` (unlit, the stage's blend, no shadows): CGE's depth test is `less`, so a coplanar copy would never be drawn.
- `deform sprite`: every 4 vertexes are a quad, replaced by a `Billboard` (axis 0 0 0) of the same size at its center; the scene holding sprites gets `ProcessEvents`. Other deforms are drawn undeformed.
- Glass: a material whose stages are all special (`cubeMap` with `texgen reflect`, `fragmentProgram heatHaze`, `mirrorRenderMap`, videos) is `DrawAsGlass`: a faint additive tint (`GlassAppearance`), so windows stay visible.
- Skies: a `cameraCubeMap name` stage (images `name_forward`, `_back`, `_left`, `_right`, `_up`, `_down`) or a `cubeMap name` (`_px`, `_nx`, `_py`, `_ny`, `_pz`, `_nz`) with `texgen skybox` / `wobblesky` marks a sky material. Its surfaces aren't drawn (no diffuse map / plain stage), and `TViewPlay.SetupSky` puts the first sky of the map's areas on a `TCastleBackground`: Doom 3 +X / +Z (up) / +Y (left) are CGE +X / +Y / -Z, and CGE draws `TexturePositiveZ` at -Z. The images' orientation within each face is not verified against real Doom 3 skies yet.

## Shadows

- CGE renders stencil shadow volumes for one light: the light node with `shadowVolumes` and `shadowVolumesMain`; in the shadowed pass CGE switches off lights with `shadowVolumes` (also global lights of other scenes). Doom 3 shadows every light, so `TDoom3Map.UpdateShadowLight` (called from `UpdateVisibility`) picks the most useful one every frame: the strongest light at the player (`LightStrengthAt`: color times `LightVolumeStrength`, the same volume / shape / falloff as the shader), lights whose origin is in the player's area first (area walls don't cast shadows, so a light behind a wall must not be chosen), ambient lights never, switching only when another light is 20% stronger.
- Walls and pillars: the area render geometry is open (no back faces), so CGE can't use it for shadow volumes. The `.cm` world brushes whose contents block light (`solid`, `opaque`) are closed convex solids: `BrushPolyhedron` rebuilds each one by clipping a large quad on every plane (centered on the brush) by all the other planes, shrinks it by 1 unit and welds the vertexes shared by faces to exactly equal coordinates (CGE matches silhouette edges with `PerfectlyEquals`). `BuildShadowCasterNode` makes one black unlit shape per brush (a shape with any open edge would be skipped). They are real, opaque geometry, because CGE only renders shadow volumes of visible scenes, but 1 unit inside the walls they are never seen. They are grouped per area (`ShadowCasters<N>` scenes) and exist only while their area is visible or reached by the shadow light.
- `noshadows` materials set the X3D `Appearance.shadowCaster` to false; `noshadows` lights (or light shaders) are never the shadow light.
- Casters: brush entities, static models and md5 models. CGE finds silhouette edges by comparing edges by position (so per-face vertexes are fine) with a quadratic search, again whenever an animated mesh changes, and skips shapes with open (border) edges. md5 meshes of more than `MaxShadowCastingTriangles` (1500, console `r_md5ShadowTris`) triangles don't cast themselves (`Appearance.shadowCaster` false): `TD3Md5Instance.BuildShadowHulls` makes one closed box per joint around the joint-space positions of the weights it dominates (bias >= 0.5), scaled by `ShadowHullScale` (0.6) so it stays inside the body, drawn black and unlit under a `MatrixTransform` that `ApplyPose` sets to the joint's pose (`JointMatrix`). The box geometry never changes, so its edges stay tiny to search.
- More than one shadow casting light needs CGE: its shadow volumes use one main light, and its shadow maps work for spot / directional lights only, while Doom 3's lights are point lights or light volumes drawn as point lights with shader effects. Area scenes, the light scene and the collision scene have `CastShadows := False`: area geometry is open and big; it receives shadows (the brushes cast for it).
- The viewport's `ShadowVolumes` is on in the play design; `r_shadows 0` turns both it and `TDoom3Map.Shadows` off.

## Light shaders

- A material's first plain stage (not `blend diffusemap` / `bumpmap` / `specularmap`) keeps its color registers (`TD3Material.StageColorExpr`): `red` / `green` / `blue` / `alpha`, `rgb`, `rgba`, `color a, b, c, d` (split at top level commas) and `colored` (= `parm0..parm3`). Expressions are read to the end of the line (`TDoom3Lexer.RestOfLine`, `//` comments removed) and parsed character by character, so `time*4` needs no spaces. A missing register is 1.
- A light's parameters: `parm0..2` = `_color`, `parm3` = 1, `shaderParm0..11` override. No `texture`, or an undeclared one, behaves like Doom 3's default `colored` light. A declared shader without color registers is white, as in Doom 3.
- `TDoom3Map.Update` advances `Time` and re-evaluates lights whose registers use time (`UsesTime`) while they are on. Colors above 1 become intensity (X3D colors are 0..1); ambient lights scale `AmbientIntensity`.
- `shaderParm4` is the time offset (`SHADERPARM_TIMEOFFSET`): the light's `time` is the map time minus it.
- Not yet: `nodiffuse` / `nospecular`, the exact projection / falloff images (see Light volumes).

## Portal visibility

- Like Doom 3's renderer: `UpdateVisibility(Camera)` (every frame, from `TViewPlay.Update`) finds the camera's area with the area BSP and flows through the portals. A portal is followed when its polygon, clipped by the current view volume (the camera frustum's side planes at first), is not empty; the view volume is then narrowed to the planes through the eye and the clipped polygon's edges. An eye within 1 unit of a portal's plane passes through with the same planes. Depth and call count are capped.
- An entity whose bounding box contains a portal (a door) belongs to the areas on both of its sides, so a shut door stays visible from either room.
- Each area has its own solid and non-solid `TCastleScene` (`AreaScene`, `AreaNonSolidScene`); hidden areas get `Visible := False`, which keeps them colliding. Brush / static model entities know the areas their bounding box touches (`TD3BrushEntity.Areas`), md5 models are tested every frame at their position.
- Lights are all in the `Lights` scene (global lights). Each knows the areas it reaches (flood from its area through portals within its Doom 3 radius); a light is switched off while none of them is visible, so fewer lights reach the shaders.
- A `func_door` closes the portals inside its bounding box (grown by 16) while it is shut (`TD3Mover.Portals`), like idDoor's area portal.
- Outside the map (noclip), with `PortalCulling` off, or in the editor everything is drawn.

## Entity activation and triggers

- Like `idEntity::ActivateTargets`, firing an entity activates every entity named by its `target`, `target1`, `target2`... keys. `TD3Game.ActivateTargets(E, Delay)` only queues the firing (game time + delay); `UpdateTriggers` runs the due ones each frame, at most 1000 per frame, so loops of relays can't recurse or hang.
- `TD3Game.Activate` is `Event_Activate` per class: `light` toggles on / off (`TDoom3Map.SetLightOn`, the light's `StartOn`; portal visibility still turns lights in hidden areas off), `trigger_relay` fires its targets after `delay`, `trigger_count` every `count` activations, `trigger_once` / `multiple` fire (or become touchable after `triggerFirst`), `trigger_hurt` switches on / off, `speaker` starts / stops, `func_door` unlocks or opens / closes, `monster_*` appear (`hide`) or wake up (`trigger`), entities with a `hide` key show / hide (`TD3BrushEntity.SetHidden`, `Scene.Exists`, so they don't collide either), `func_remove` hides its targets for good. Other classes are logged once (`Not supported yet: activating <class>`), as are `call` keys (script functions).
- Trigger volumes: brush triggers have no render geometry (their material is `trigger`, not drawn), only a `.cm` model named like the entity, in entity-local coordinates: `SpawnTrigger` places its vertices at the origin (rotated) and takes their box. The player's box (feet to eye + 6, radius 16) touching it fires `trigger_once` (then disabled) and `trigger_multiple` (again after `wait`); `trigger_hurt` damages every `delay` seconds by the `damage` of its `def_damage` entityDef.

## Movers

- `TDoom3Map.Rebuild` merges each entity's entityDef (`classname`, `inherit` chains) into its keys first, skipping `editor_*`: the map's keys win, like Doom 3's spawn args. So `func_door` gets its def's speed, `triggersize`, sounds, `func_rotating` its `start_on`.
- `func_door` (`TD3Mover`, `mkDoor`): like `idDoor`, it travels the size of its *world* bounds along `movedir` minus `lip` (most retail doors are rotated), and opens when the player's eye enters those bounds grown by `triggersize` (default 60). Doors with the same `team` open, close and lock together (`TD3Game.OpenTeam` / `CloseTeam` / `LockTeam`). A door's area portals are closed while it is shut.
- `target_lock` locks (`locked` 1) or unlocks (0) its target doors and their teams. Activating a locked door unlocks it.
- `func_rotating` (`mkRotating`) turns while `Running` (`start_on`); activation stops / starts it.
- `bind`: brush entities and static / md5 models named by another entity's `bind` follow it (`TD3Binding`: the child's transform relative to the parent's at spawn, reapplied with `MatrixDecompose` when the parent moved). Bound lights and binding to md5 joints (`bindToJoint`) are not done; `func_mover` / `func_elevator` paths come with scripts (roadmap 5c).

## Scripts

- `TD3Game.StartScripts` (end of `Spawn`) compiles `script/doom_main.script` (it `#include`s the game's other scripts, map scripts included) and then `maps/<map>.script` into one `TD3ScriptVM`, like idProgram. A compile error turns scripts off for the map (logged). Then, like idWorldspawn, the map script's global `main` and worldspawn's `call` keys start on the first frame; triggers' `call` keys start when they fire their targets (idTrigger::CallScript).
- The compiler follows idCompiler: types `void float boolean vector string entity` and `object` types (fields and methods, called virtually by name), namespaces (`a::b`), globals with constant initializers, `scriptEvent` declarations of engine events, `$name` entities, `'x y z'` vectors and their `name_x` components, `thread f()`, `int()`. Priorities differ from C: `& |` bind like `*`, assignments bind tighter than `&& ||`, and `&& ||` evaluate both sides. `#define`s (with parameters too) stay defined for the files compiled later.
- The VM is a stack machine with one value stack and call stack per thread, so a thread can stop in the middle of nested calls: `sys.wait` (game time), `waitFrame`, `waitFor` (until `TD3ScriptHost.EntityBusy` is false: a script mover or a door still moving), `waitForThread`. `thread f()` runs the new thread at once until it waits. A thread running a million instructions in one frame is stopped (runaway loop). Events the VM handles itself (waiting, threads, printing, math, strings) work on any target; the others go to `TD3GameScriptHost` → `TD3Game.ScriptEvent`; unknown ones are logged once (`Not supported yet: event "x"`) and return their type's default.
- Entity handles are indexes in the map's entity list + 1 (0 is `$null_entity`).
- `TD3ScriptMover` (created on an entity's first mover event) keeps Doom 3 origin and angles, relative to the master when the entity is bound (then the script moves change `TD3Binding.ChildInParent`), and interpolates `move` / `moveTo` / `moveToPos` (over `time`, or distance / `speed`) and `rotateOnce` / `rotateTo` (over `time`) with idMover's acceleration and deceleration times; `rotate` turns until `stopRotating`. Bindings are updated parents first, so chains of bound machine parts follow in the same frame.
- `setGuiParm` sets the entity's key (`gui_parm1`...) and redraws its GUI screens: `TDoom3Map.SetGuiParm` finds the `d3gui:` textures of the entity's scene, gets each one's GUI file back from the GUI cache (`GuiUrlPath`) and points the texture at the GUI drawn with the new state (drawn once per state, then cached).
- `startSpline` moves a script mover along the `curve_*` key of a `func_splinemover` (control points in map coordinates, evaluated as a clamped uniform cubic B-spline like idCurve_NURBS with equal weights) over `time` (or the curve's length / `speed`), turning it with the curve's direction from the angles it had.
- Sounds from scripts (`startSoundShader`, `startSound` with a `snd_` key, `stopSound`) play on a `TCastleSoundSource` behavior of the entity's scene (or of a transform at its origin); a sound on a channel other than 0 replaces the channel's previous one.
- Not done yet: script objects on entities (monsters' and weapons' AI, roadmap 5d), `setColor` / `setShaderParm` on brush entities and models (their materials' parms), bound lights.

## Cinematics

- Activating an entity whose entityDef has `spawnclass` `idCameraAnim` (for example `marscity_cinematic_cam`) loads the file of its `anim` (the def's `anim <name>` key, `x.camera` meaning `x.md5camera`) into a `TD3CameraAnim` (cached) and makes it the view: `TD3Game.CinematicView` samples it at the time since the start, plus `origin - old_origin`. Like idCameraAnim, playback skips one frame at each cut and doesn't blend into the next shot; the frame's quaternion turns the camera's +X (forward) and +Z (up) like md5 joints (checked: Mars City's first camera looks at its console screen 17 units away, like in dhewm3). At the end (after `cycle` loops) the camera fires its targets, usually the next shot. `idCameraView` (`func_cameraview`) shows the view from the entity (or towards `cameraTarget`).
- `TViewPlay.UpdateCinematic` moves the camera there, sets the horizontal field of view, hides the HUD and stops the walk navigation; the player stays where they were (triggers keep using that position). _Escape_ (console `skipcinematic`) stops the camera and, for a second, every camera started after it, so a chain of shots is skipped.
- `trigger_fade` (`idTrigger_Fade`) and `sys.fadeIn` / `fadeOut` / `fadeTo` fade `TD3Game.FadeColor` (RGBA) from its current value; the view draws it with the `FadeRect` control of the design. `info_player_teleport` (`idPlayerStart`) sets a teleport that the view applies (after the cinematic).
- Lights fade with `TD3LightInfo.Fade` (a scale of the light's color, `TDoom3Map.SetLightFade`): `fadeOutLight` / `fadeInLight` change it over time (an off light comes on dark first).
- `idAnimated` md5 entities (`TD3Animated`): at spawn they show the first frame of `anim` (`TD3Md5Instance.SetFrame`, paused) or loop `start_anim`; `wait` activates them after that many seconds. Activation shows them and plays `anim` (`cycle` times, -1 forever) or the next of `anim1`..`anim<num_anims>`; at the end of each anim (`AnimLength` x cycles) they fire their targets, then are removed (`remove`), play the next anim (`auto_advance`) or can be activated again.
- Cinematic characters (`cinematic` `1`, idAI in Doom 3): activation shows them and plays their `anim` once, holding its last frame; their head plays its own anim of the same name (lip sync). Their AI script and `path_anim` paths are roadmap 5d.
- Heads (`def_head`, a model decl, at the body's `head_joint`; `TDoom3Map.BuildHead`): a second `TD3Md5Instance` in a transform under the body's holder, moved every frame to the joint, turned by the joint's rotation since its bind pose (`JointTransform`: head meshes are upright for the bind pose, so the joint's own bind orientation must not turn them). The map log line counts them (`(N with heads)`).
- Not done yet: screen GUIs changing during the cinematic (GUI scripts, item 4); shadows of the big moving models (the hangar's ship and doors) make some hangar shots dark.

## Actors (AI scripts)

- `TD3Game.SpawnActors` (after the scripts compiled) makes a `TD3Actor` for each idAI md5 entity whose `scriptobject` is a `character` (or derives from it), except monsters (they keep the game's simple AI for now) and cinematic characters (they play their `anim` when activated). The actor owns a `TD3ScriptObject` of that type (`TD3GameScriptHost.EntityObject` gives it to the VM: `self`'s fields, methods by name).
- Like idActor, the main thread runs the object's `init`, then state functions: `setState` / `setNextState` choose the next one, which `UpdateActors` starts in the main thread on the next frame (`TD3ScriptVM.RestartThread`; `setState` also stops the current thread now with `Yield`). Each animation channel (torso, legs, head, eyelids; `ANIMCHANNEL_ALL` means the legs) has its own thread for `animState` functions (`Legs_Idle`, `Legs_Walk`...). These threads are `Persistent`: the VM keeps them when their function ends.
- Animations: torso and legs play on the body's md5 instance (the last call wins), the head channel on the head. `animDone` compares the time since `playAnim` with the anim's length minus the blend frames (24 per second); cycles are never done.
- Movement: `moveToEntity` / `moveToPosition` walk straight to the goal (no AAS paths, no collisions yet) at the walk animation's speed (`TD3Md5Instance.AnimSpeed`, its origin joint's speed; the instance's `LockOrigin` keeps the mesh on the entity meanwhile), turning towards it; `turnTo` turns at `turn_rate`. Each frame the actor writes `AI_FORWARD`, `AI_MOVE_DONE`, `AI_ONGROUND`, `AI_DEST_UNREACHABLE` into its object; activation sets `AI_ACTIVATED`.
- `waitAction` makes the thread wait (`TD3ScriptThread.WaitFor` the actor) until `finishAction`; `callFunction` / `hasFunction` (in the VM) call the object's method by name in the current thread, which is how characters run their path commands (`callFunction( "path_corner" )`).
- Monsters whose script object is in `ScriptedMonsterObjects` (`monster_zombie`, and `monster_test` of the test level) are actors too; they keep their `TD3Monster` for health and shots (its simple AI off: `TD3Monster.Actor`). The player is their only enemy, with a handle of its own for scripts (`PlayerHandle`: `getOrigin`, `getName`, `getHealth`): `checkForEnemy` / `findEnemy` see it within `MonsterSightRange` (and a 180 degree field of view), `moveToEnemy` chases it (the goal follows it, done within `melee_range`; monsters move with `StepTowards`, the collision and floor following of the simple AI), `AI_ENEMY_VISIBLE` / `AI_ENEMY_IN_FOV` / `AI_ENEMY_DEAD` are kept up to date. A shot sets `AI_PAIN` for a frame and makes the player the enemy; a deadly one sets `AI_DEAD` and starts `state_Killed` (the zombies then `stopThinking`; the body sinks like the simple AI's).
- Animations: torso and legs channels play on one body, so each frame the body plays the torso's action (a `playAnim` not done yet), else the legs' anim, else the torso's idle. Names resolve like idDeclModelDef: `idle` is one of `idle1`..`idle3` at random (`ResolveAnim`), chosen when the script asks (so `animDone` knows its length).
- Frame commands (`TD3ModelDecl.FrameCommands`, fired by `TD3Md5Instance.OnFrameCommand` as the anim passes their frame): `melee <damage def>` hurts the player when in reach (the def's `damage`), `sound*` plays the entity's `snd_` key.
- Not done yet: the other monsters' scripts (imps, security zombies: projectiles, `attack_missile`, `getCombatNode`...), talking (`AI_TALK`, the player's use), heads looking at the player, AAS navigation, pushing, cowering, ragdolls.

## Rendering notes

- Each area's solid surfaces are one `TCastleScene` and its `nonsolid`, translucent and blended surfaces another with `Collides := False`; each material is its own shape, so frustum culling and per-shape light lists stay effective (`MaxLightsPerShape` 32).
- Lights are `Global` in the `Lights` scene with `CastGlobalLights`, so they light every area, brush entity and md5 model.
- Brush entity, static model and md5 scenes are children of `TDoom3Map`. Static model entities are `TD3BrushEntity` items too, so `func_door` / `func_rotating` with LWO models move like brush ones; md5 scenes don't collide and aren't pickable (shots test monsters as cylinders).
- Textures are referenced by URL (`d3fs:/...`, `d3img:/...`), so CGE's texture cache shares them between shapes and scenes. X3D nodes are never shared between scenes.
