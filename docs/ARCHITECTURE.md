# Architecture

Castle Doom 3 reads Doom 3 (id Tech 4) data at runtime and turns it into Castle Game Engine (CGE) scenes. Nothing is converted offline.

```
 PK4 / loose files ──► Doom3Files (d3fs:) ──┬─► Doom3Lexer ─► Doom3Decls (materials, entityDefs, models, skins, sounds)
                                            │                    │
                                            │                    ├─► Doom3Images (d3img:, image programs)
                                            │                    └─► Doom3Materials (X3D appearances)
                                            ├─► Doom3Proc   (.proc areas, brush models, portals, BSP)
                                            ├─► Doom3MapFile (.map entities)
                                            ├─► Doom3Md5    (.md5mesh / .md5anim, CPU skinning)
                                            ├─► Doom3StaticModels (.lwo / .ase)
                                            ├─► Doom3Collision (.cm)
                                            └─► Doom3Portals (portal visibility)
                                                         │
                                       Doom3Level (TDoom3Map component) ─► Doom3World (TD3Game: doors, AI, sounds, player)
                                                         │
                                         GameViewPlay / GameViewMenu, Doom3Hud, Doom3Console
```

## Units

| Unit | Role |
|---|---|
| `Doom3Files` | Virtual file system. Reads each PK4's ZIP central directory once, indexes paths (lowercase, `/`), memory maps the PK4 files and inflates entries on demand straight from the mapping (the C zlib CGE loads on Windows, FPC's inflate elsewhere), so 300 MB+ paks are never read whole. Loose directories override PK4s. Registers `d3fs:`. Also the load profiler (`LoadProfileStart` / `LoadProfileStep` / `LoadProfileLog`). |
| `Doom3Lexer` | idLexer subset shared by all text formats: quoted strings, punctuation, `//` and `/* */` comments, paths as single tokens, locale-independent numbers, `SkipBracedSection`. |
| `Doom3Decls` | Scans `materials/*.mtr`, `def/*.def`, `skins/*.skin`, `sound/*.sndshd` and indexes every declaration body by type and name (first definition wins, like Doom 3). Bodies are parsed on demand into `TD3Material`, `TD3ModelDecl`, `TD3Skin`, `TD3SoundShader` and merged entityDef dictionaries (`inherit`). Undeclared materials become implicit ones named after their image. |
| `Doom3Images` | Finds image files (`.tga`, `.png`, `.jpg`, `dds/*.dds`) and evaluates image programs. Normal maps are served as `d3img:/normal/<program>`: plain Doom 3 normal maps get their green channel flipped, `heightmap(img, scale)` becomes a normal map, `addnormals(a, b)` adds slopes. Output is uncompressed TGA. |
| `Doom3Materials` | `TD3Material` → `TAppearanceNode`: Phong material with diffuse, normal and specular textures (shininess 16/128, Doom 3's exponent), alpha test → `amMask`, translucent → `amBlend`; blended stages → unlit material with `TBlendModeNode` (`add` = one/one, `filter` = dst_color/zero). |
| `Doom3Proc` | `mapProcFile003`: models with surfaces (`( x y z s t nx ny nz )` vertexes, indexes), `interAreaPortals`, `nodes` (area BSP, `PointInArea`). Shadow models are skipped. |
| `Doom3MapFile` | `.map` entities (key / value pairs, primitive count; brushes and patches skipped), `origin` / `angle` / `rotation` helpers, coordinate conversion. |
| `Doom3Md5` | md5mesh joints / meshes / weights, md5anim hierarchy / baseframe / frames, absolute poses, frame interpolation (lerp + normalized quaternion lerp), skinning. `TD3Md5Instance` owns a `TCastleScene`, `PlayAnim`, `Update`. `Md5Cache` shares parsed files. |
| `Doom3StaticModels` | LWO2 (`TAGS`, `LAYR`, `PNTS`, `VMAP` / `VMAD` `TXUV`, `POLS` `FACE` as triangle fans, `PTAG` `SURF`) and ASE (`*MATERIAL` / `*SUBMATERIAL` `*BITMAP` and UV tiling / offset, `*GEOMOBJECT` meshes, `*MESH_MTLID`, `*MATERIAL_REF`). Surfaces per material with Doom-style smooth normals (vertexes sharing position and UV). `StaticModels` caches them. |
| `Doom3Collision` | `.cm` files: per `collisionModel` the vertices, edges (edge 0 is a dummy; a negative edge in a polygon is used backwards and starts at its second vertex), BSP nodes (counted), polygons (`numEdges ( edges ) ( normal ) dist ( min ) ( max ) "material"`) and brushes (`n { ( normal ) dist ... } ( min ) ( max ) "contents"`). `PlayerTriangles` / `BuildCollisionNode` turn the polygons whose material `BlocksPlayer` into triangle fans. |
| `Doom3Expressions` | Material expressions as trees (`TD3Expr.Eval`, `IsConstant`, `UsesTime`) parsed with Doom 3's operator priorities, and `TD3Table` (`snap`, `clamp`, the first value copied to the end, lookups like `idDeclTable::TableLookup`). |
| `Doom3LightEffects` | Doom 3 light volumes: `PointLightMatrix` / `ProjectedLightMatrix` (CGE world -> the light's texture space `(s w, t w, q, w)`), `LightTexCoord`, `CreateLightEffect` (per-light GLSL with a uniquely named matrix uniform), `LightLibraryEffect` / `AddLightLibrary`, `ProjectionShape`. |
| `Doom3Portals` | `TD3PortalVisibility`: the portals in CGE coordinates, per area portal lists, `Compute` (portal flow with polygon clipping and per-portal narrowing, closed portals), `AreasWithinRadius` (areas a light reaches), `PortalsInBox` (portals a door closes), `FindPortal` (the portal an `info_locationSeparator` touches), `ClipPolygon`. |
| `Doom3Gui` | `.gui` files: `TD3Gui` / `TD3GuiWindow` (windowDef, editDef, choiceDef... trees; properties as comma-separated tokens; events and variable declarations skipped), `RenderGui` (software rendering), `GuiImageUrl` (cache per path and state, `d3gui:` protocol), `GuiSurfaceUrl` / `GuiSurfPath` (guisurf keywords). |
| `Doom3Aas` | AAS files (`maps/<map>.aas48`, "DewmAAS" text): planes, BSP nodes (`PointAreaNum`, `OriginAreaNum`), areas with their reachabilities (travel type, target area, start / end points, travel time); `FindPath` is a Dijkstra search over areas. The geometry, portal and cluster sections are skipped. |
| `Doom3Efx` | `efxs/<map>.efx` reverb files like dhewm3's idEFXFile: `reverb "<name>" { ... }` blocks of EAX reverb parameters (quoted keys like `"decay hf ratio"`; gains in millibels) become `TCastleSoundReverb`s; `Select` picks one like dhewm3 (area number, location, `"default"`). |
| `Doom3Camera` | `.md5camera` camera anims: `TD3CameraAnim` (frames, cuts, `Sample` at a time). |
| `Doom3Scene` | `TD3Scene`, the `TCastleScene` of all map geometry and models: it prepares shadow volume edges only when it casts shadows (see "Performance"). |
| `Doom3Sampler` | A sampling profiler (Windows x86_64): records the main thread's stack every millisecond into `samples.txt`; `tools/resolve_samples.py` and `tools/sample_callers.py` read it with the linker map. |
| `Doom3Script` | Doom 3 scripts: `TD3ScriptVM` compiles the whole program (preprocessor, idCompiler's grammar and operator priorities, objects) to a stack machine and runs its threads; events other than the threads' own go to a `TD3ScriptHost`. |
| `Doom3Level` | `TDoom3Map` (`TCastleTransform`, registered for the editor): builds the area scenes, lights, brush entities and md5 entities of a map. |
| `Doom3World` | `TD3Game`: movers (`func_door`, `func_rotating`), speakers, monsters, triggers and entity activation, player health / armor, pistol, use. |
| `Doom3Hud`, `Doom3Console` | UI components drawn with `DrawRectangle` and `UIFont`. |
| `GameViewPlay`, `GameViewMenu`, `GameInitialize` | Views, input, demo-script harness, data source setup and command line. |

## Coordinates and conventions

- Doom 3 is X forward, Y left, Z up; CGE is Y up. `D3ToCge(v) = (v.x, v.z, -v.y)`, a proper rotation, so triangle winding is preserved. 1 unit = 1 Doom 3 unit (an inch): player eye height 68, radius 16, speeds 140 / 220, gravity on.
- Doom 3 front faces are clockwise (its face plane is `(v2 - v0) × (v1 - v0)`), so geometry sets `Ccw := False`; `twoSided` materials set `Solid := False`.
- Doom 3's `t` texture coordinate goes down the image, CGE images are bottom-to-top: `v = 1 - t`. Because of this flip, the tangent-space bitangent points the other way, hence the green flip of normal maps.
- md5 quaternions store x, y, z; w is `-sqrt(1 - x² - y² - z²)`. Joint poses are made absolute by `parent.q * local.q` and `parent.pos + parent.q.rotate(local.pos)`.
- Entity rotation: idMat3 rows are the rotated local axes (`world = x·row0 + y·row1 + z·row2`). `D3RotateCge` applies it to CGE vectors; `SetD3Rotation` orients a transform with it. CGE's default `TCastleTransform.Orientation` is `otUpYDirectionZ` (direction = local **+Z**), which `SetD3Rotation` respects; a unit test checks that yaw 135 turns a model's +X to (cos 135, sin 135).
- Static models: LightWave points are read as Doom 3 `(x, z, y)`. That only relabels left-handed Y-up axes as right-handed Z-up ones (right, forward and up stay the same), it isn't a mirror: LWO polygons stay clockwise from the front, Doom 3's own style, so `LoadLwo` reverses its triangle fans. (Until October 2026 the port assumed a mirror and drew LWO models inside out: one-sided panels vanished, like the back wall of Mars City Underground's starting elevator, which dhewm3 culls from outside.) Doom 3 flips ASE faces (A, C, B) to its clockwise style, so ASE files are counter-clockwise. Both use `Ccw := True`. Doom 3's `t = 1 - v`, so CGE uses the files' `v` directly. ASE materials are the `*BITMAP` path from `base/` on, without the extension.
- With `r_lightVolumes 0`, a point light's CGE radius is the size of its Doom 3 light box (the largest `light_radius`) with `RadiusFalloff` (CGE change H, `doom3-port`: glTF's `(1 - (d/r)^4)^2`, fading to zero at the radius) and attenuation `1 / (1 + 2 d² / r²)`: 0.59 of the center's light at half the radius, roughly Doom 3's round falloff; projected lights are spot lights fading at 1.2 times `light_target`. With light volumes (the default) the effect computes Doom 3's falloff, and the radius only bounds which shapes get the light. The flashlight and the muzzle flash use `RadiusFalloff` too.
- Sound shader distances are meters (× 39.37 units); volume is dB.

## Collision

- With a `maps/<name>.cm` (and `UseCollisionModel`), `TDoom3Map` loads the `worldMap` model into `WorldCollision`: invisible (`Visible := False`), `PreciseCollisions`, not pickable. The area scenes then have `Collides := False`. So the player and `WorldSegmentCollision` (monster sight, monster movement) use Doom 3's collision geometry with its `playerclip` brushes and without render-only detail, while `WorldRayCast` (shots, monster floor following) hits what you see.
- Contents come from the polygon's material, like Doom 3's surface parameters: `playerclip` blocks the player only; `monsterclip`, `nonsolid`, `water`, `trigger`, `ikclip`, `aassolid`... clear solid (`TD3Material.BlocksPlayer`).
- Brush entities (doors, movers) keep colliding with their render geometry, which moves with them; their `.cm` models are parsed but not used yet. Without a `.cm`, the render geometry collides as before.

## Light volumes

- Doom 3 lights don't fade with distance: a lit point is mapped into the light's texture space (`R_DeriveLightData`'s `lightProject`) and lit only inside 0..1. Point lights are boxes (`light_radius` around the origin, rotated by `rotation`; `light_center` only moves where the light comes from); projected lights are pyramids from the origin along `light_target`, `light_right` / `light_up` being half the width / height at the target, the falloff running from `light_start` to `light_end` (or the target).
- `TDoom3Map.BuildLights` makes every light a `TPointLightNode` without attenuation whose `Radius` only bounds CGE's per-shape light lists (the box's corner, the frustum), with an `Effect` from `CreateLightEffect`. The GLSL plugs `PLUG_light_scale`: `p = d3_light_matrix_N * (castle_CameraInverseMatrix * castle_vertex_eye)` gives the fragment's light coordinates; outside the volume the light adds nothing, inside it is scaled by the projection and falloff shapes.
- `castle_vertex_eye` is the Phong shader's varying (CGE's default shading is Phong, so light code runs per fragment) and `castle_CameraInverseMatrix` comes from CGE's `castle-shader:/EyeWorldSpace.glsl` library. Light effects can't enable libraries, appearance / group effects can: every scene the map builds (areas, brush entities, static and md5 models) gets `AddLightLibrary` on its root, otherwise the matrix is zero and map lights add nothing to it.
- Projection and falloff **images** are approximated analytically: textures referenced only by light effects are not bound by CGE's renderer (they read as black / garbage). `ProjectionShape` picks a center-bright soft square for `square*` images, a full volume for `bright` / `white`, otherwise a soft disc; the depth falloff follows Doom 3's default point / projected falloff images.
- Uniform names must be unique per light (several lights' code ends up in one shader), so they are suffixed with the light's index.
- Shared effects (CGE change K, `doom3-port`): when the CGE supports custom fields on lights (`SharedLightEffectsAvailable`), `SetLightVolume` gives all lights of one kind (`TD3SharedLightEffects`: light shape, projected or not) one `Effect` whose code uses `d3_light_matrix_<Light>`, and each light a custom field `d3_light_matrix_` with its matrix; CGE sets it per shape as `d3_light_matrix_<light number>`. Shapes lit by the same kinds of lights then share shader programs. The log says `Light volumes: N lights share M effects (per-light uniforms)`; console `r_sharedLightEffects 0` (or env `CD3_SHARED_LIGHT_EFFECTS=0`) uses an effect per light.
- `r_lightVolumes 0` (`Doom3LightEffects.LightVolumes`) reloads the map with plain spheres / X3D spot lights for comparison.

## GUIs

- A material with `guisurf entity` (`entity2`, `entity3`) shows the GUI named by its entity's `gui` (`gui2`, `gui3`) key; `guisurf guis/x.gui` names it directly. `TDoom3Map.BuildProcModel` (brush entities pass their entity) and `TD3StaticModel.BuildNode` (static models pass the entity's keys) give such surfaces `GuiAppearance`: unlit, opaque, the GUI image as emissive texture, using the surface's own texture coordinates (Doom 3 maps the 640 x 480 GUI onto them).
- `RenderGui` draws the window tree in software, so it needs no OpenGL and unit tests can check pixels: background colors, a background material's image (scaled, tinted by `matcolor`), borders, and word-wrapped text with CGE's built-in UI font (`CastleTextureFont_DefaultUi`): every glyph is scaled from the font atlas (Doom 3 fonts are 48 pixels at `textscale 1`) and placed like CGE does, at `pen x - G.X`, `baseline - G.Y`. `gui::name` texts read the GUI state: the entity's keys.
- Properties are read as tokens separated by commas (`rect 0, 0, 640, 480`), so one-line `windowDef x { rect ... backcolor ... }` blocks work; `definevec4` / `float`... declarations have a name before the value.
- Images are cached per GUI path and `gui_*` state and served as `d3gui:/guiN.tga` (TGA), so CGE's texture cache shares them. Not yet: events and scripts (`onTime` transitions, `onAction`), the cursor and interaction, Doom 3's fonts, `rotate` / `shear`.

## Material stages

- `TD3Material` keeps the texture matrix keywords of its diffuse stage (`DiffuseTexOps`) and of its first plain stage (`StageTexOps`): `scroll` / `translate`, `scale`, `centerScale`, `shear`, `rotate` (in cycles, around the texture center), each with expressions. `TexMatrix` composes them like idMaterial's `MultiplyTextureMatrix` (a new keyword applies after the previous ones) and converts to CGE's texture coordinates (`v = 1 - t`: `F M F` with `F (s, v) = (s, 1 - v)`), as a 4x4 matrix for a `TextureTransformMatrix3D` node.
- `MaterialAppearance` adds that node to the appearance (the diffuse stage's matrix applies to the normal and specular maps too) and sets the plain stage's color registers on the unlit material (`EmissiveColor`, and `Transparency` for `blend blend` stages). Appearances that change with time (`UsesTime`) are registered; `TDoom3Map.Update` calls `UpdateAnimatedSurfaces(Time)` every frame and `ClearMap` forgets them. World surfaces use shader parameters 1.
- More stages: plain stages after the first one are kept in `TD3Material.ExtraStages` (image, blend, color registers, texture matrix, alpha test). `OverlayCount` stages are drawn over the base appearance: for lit materials the first plain stage too, otherwise only the extra ones. `BuildProcModel` and static models add one shape per overlay on the same triangles with `OverlayAppearance` (unlit, the stage's blend, no shadows) and a CGE `DepthMode` with `depthFunc "lequal"`, like Doom 3 (alpha-tested stages also get a polygon offset, since their surface may be drawn after them).
- `deform sprite`: every 4 vertexes are a quad, replaced by a `Billboard` (axis 0 0 0) of the same size at its center; the scene holding sprites gets `ProcessEvents`. Other deforms are drawn undeformed.
- Glass: a material whose stages are all special (`cubeMap` with `texgen reflect`, `program heatHaze*`, `mirrorRenderMap`, videos) is `DrawAsGlass`. `GlassAppearance` draws its heat haze if it has one, otherwise its reflection, otherwise a faint additive tint (mirrors, videos), so windows stay visible.
- Heat haze: the parser keeps the first stage with a `heatHaze*` program: `fragmentMap 1` (the distortion normal map), `fragmentMap 2` of the `WithMask` programs (the mask), `vertexParm 0` (the scroll, expressions) and `vertexParm 1` (the magnitude). The appearance is unlit with blending (so it's drawn after the opaque shapes), and an `Effect` does what `glprogs/heatHaze*.vfp` do: it samples a CGE `ScreenTexture` (the colors rendered so far) at the fragment's screen position, moved by the normal map (scrolled; `HazeScrolls` are updated with the other animated surfaces) times `min(P00 / max(-z_eye, 1), 0.02) * magnitude`; with a mask, fragments where it is below 0.01 are dropped. The shape has Phong shading (the effect needs `castle_vertex_eye`).
- Reflections: the first `cubeMap` stage with `texgen reflect` gives `ReflectCubeMap` and its color registers. `ReflectionAppearance` is a `ComposedCubeMapTexture` of the six images (`_px`... mapped to CGE axes like the skies, `CubeMapUrls`), on an unlit material with the stage's color, added (`one, one`); `SetupSpecialShape` gives the shape a `TextureCoordinateGenerator` `WORLDSPACEREFLECTIONVECTOR`. Glass draws it instead of the tint; lit and plain materials get it as one more overlay (on the same triangles, `lequal`). Missing cube map images: no reflection (glass falls back to the tint).
- Skies: a `cameraCubeMap name` stage (images `name_forward`, `_back`, `_left`, `_right`, `_up`, `_down`) or a `cubeMap name` (`_px`, `_nx`, `_py`, `_ny`, `_pz`, `_nz`) with `texgen skybox` / `wobblesky` marks a sky material. Its surfaces aren't drawn (no diffuse map / plain stage), and `TViewPlay.SetupSky` puts the first sky of the map's areas on a `TCastleBackground`: Doom 3 +X / +Z (up) / +Y (left) are CGE +X / +Y / -Z, and CGE draws `TexturePositiveZ` at -Z. The images' orientation within each face is not verified against real Doom 3 skies yet.

## Shadows

- CGE renders stencil shadow volumes for one light: the light node with `shadowVolumes` and `shadowVolumesMain`; in the shadowed pass CGE switches off lights with `shadowVolumes` (also global lights of other scenes). Doom 3 shadows every light, so `TDoom3Map.UpdateShadowLight` (called from `UpdateVisibility`) picks the most useful one every frame: the strongest light at the player (`LightStrengthAt`: color times `LightVolumeStrength`, the same volume / shape / falloff as the shader), lights whose origin is in the player's area first (area walls don't cast shadows, so a light behind a wall must not be chosen), ambient lights never, switching only when another light is 20% stronger.
- Walls and pillars: the area render geometry is open (no back faces), so CGE can't use it for shadow volumes. The `.cm` world brushes whose contents block light (`solid`, `opaque`) are closed convex solids: `BrushPolyhedron` rebuilds each one by clipping a large quad on every plane (centered on the brush) by all the other planes, shrinks it by 1 unit and welds the vertexes shared by faces to exactly equal coordinates (CGE matches silhouette edges with `PerfectlyEquals`). `BuildShadowCasterNode` makes one shape per brush (a shape with any open edge would be skipped), invisible (`Shape.Visible := False`): shadow-only casters, whose shadow volumes CGE renders with caps since they aren't in the depth buffer (CGE change G, `doom3-port`). The 1 unit inset keeps their light caps off the walls' depth. They are grouped per area (`ShadowCasters<N>` scenes) and exist only while their area is visible or reached by the shadow light.
- Precomputed shadow volumes: dmap writes `shadowModel "_prelight_<light>"` into the `.proc` for static lights: the shadow volume of the world and static models from that light (`TD3ProcFile.FindShadowModel`; header `numVerts noCaps noFrontCaps numIndexes planeBits`, the indexes are sides, then far caps, then near caps). CGE can't take a ready shadow volume, but the volume used as an invisible caster for its own light casts the same region inside the light's bounds. `TDoom3Map.PrelightScene` builds it when its light first becomes the shadow light (`Ccw` from its signed volume), and `SetShadowLight` shows only the current light's (`PrelightShadows`, console `r_prelightShadows`). Only ~10% of the demo's volumes are closed by exact edge matching (T-junctions), so the scene has `RenderOptions.WholeSceneManifold` (border edges cast too).
- `noshadows` materials set the X3D `Appearance.shadowCaster` to false; `noshadows` lights (or light shaders) are never the shadow light.
- Casters: brush entities, static models and md5 models. CGE finds silhouette edges by comparing edges by position (so per-face vertexes are fine; in linear time with CGE change N) and skips shapes with open (border) edges; when only an animated mesh's coordinates change, it keeps the edges and moves the same caster triangles (CGE change F, `doom3-port`). md5 models of more than `MaxShadowCastingTriangles` (1500, console `r_md5ShadowTris`) triangles cast with their own triangles when all their meshes are closed in the bind pose (`TD3Md5Model.MeshClosed`, `ClosedMeshesCastShadows`, console `r_md5ShadowClosed`; open meshes wouldn't cast at all). Otherwise they don't cast themselves (`Appearance.shadowCaster` false): `TD3Md5Instance.BuildShadowHulls` makes one closed box per joint around the joint-space positions of the weights it dominates (bias >= 0.5), scaled by `ShadowHullScale` (0.6) so it stays inside the body, invisible shadow-only casters (like the brush casters) under a `MatrixTransform` that `ApplyPose` sets to the joint's pose (`JointMatrix`). The box geometry never changes, so its edges stay tiny to search.
- More than one shadow casting light needs CGE: its shadow volumes use one main light, and its shadow maps work for spot / directional lights only, while Doom 3's lights are point lights or light volumes drawn as point lights with shader effects. Area scenes, the light scene and the collision scene have `CastShadows := False`: area geometry is open and big; it receives shadows (the brushes cast for it).
- The viewport's `ShadowVolumes` is on in the play design; `r_shadows 0` turns both it and `TDoom3Map.Shadows` off.

## Light shaders

- A material's first plain stage (not `blend diffusemap` / `bumpmap` / `specularmap`) keeps its color registers (`TD3Material.StageColorExpr`): `red` / `green` / `blue` / `alpha`, `rgb`, `rgba`, `color a, b, c, d` (split at top level commas) and `colored` (= `parm0..parm3`). Expressions are read to the end of the line (`TDoom3Lexer.RestOfLine`, `//` comments removed) and parsed character by character, so `time*4` needs no spaces. A missing register is 1.
- A light's parameters: `parm0..2` = `_color`, `parm3` = 1, `shaderParm0..11` override. No `texture`, or an undeclared one, behaves like Doom 3's default `colored` light. A declared shader without color registers is white, as in Doom 3.
- `TDoom3Map.Update` advances `Time` and re-evaluates lights whose registers use time (`UsesTime`) while they are on. Colors above 1 become intensity (X3D colors are 0..1); ambient lights scale `AmbientIntensity`.
- `shaderParm4` is the time offset (`SHADERPARM_TIMEOFFSET`): the light's `time` is the map time minus it.
- Not yet: `nodiffuse` / `nospecular`, the exact projection / falloff images (see Light volumes).

## Portal visibility

- Like Doom 3's renderer: `UpdateVisibility(Camera)` (every frame, from `TViewPlay.Update`) finds the camera's area with the area BSP and flows through the portals. A portal is followed when its polygon, clipped by the current view volume (the camera frustum's side planes at first), is not empty; the view volume is then narrowed to the planes through the eye and the clipped polygon's edges. An eye within 1 unit of a portal's plane passes through with the same planes. Depth and call count are capped.
- An entity whose bounding box contains a portal (a door) belongs to the areas on both of its sides, so a shut door stays visible from either room.
- Each area has its own solid and non-solid `TCastleScene` (`AreaScene`, `AreaNonSolidScene`); hidden areas get `Visible := False`, which keeps them colliding. Brush / static model entities know the areas their bounding box touches (`TD3BrushEntity.Areas`), md5 models are tested every frame at their position.
- Lights are all in the `Lights` scene (global lights). Each knows the areas it reaches (flood from its area through portals within its Doom 3 radius); a light is switched off while none of them is visible, so fewer lights reach the shaders.
- A `func_door` closes the portals inside its bounding box (grown by 16) while it is shut (`TD3Mover.Portals`), like idDoor's area portal.
- Outside the map (noclip), with `PortalCulling` off, or in the editor everything is drawn.

## Entity activation and triggers

- Like `idEntity::ActivateTargets`, firing an entity activates every entity named by its `target`, `target1`, `target2`... keys. `TD3Game.ActivateTargets(E, Delay)` only queues the firing (game time + delay); `UpdateTriggers` runs the due ones each frame, at most 1000 per frame, so loops of relays can't recurse or hang.
- `TD3Game.Activate` is `Event_Activate` per class: `light` toggles on / off (`TDoom3Map.SetLightOn`, the light's `StartOn`; portal visibility still turns lights in hidden areas off), `trigger_relay` fires its targets after `delay`, `trigger_count` every `count` activations, `trigger_once` / `multiple` fire (or become touchable after `triggerFirst`), `trigger_hurt` switches on / off, `speaker` starts / stops, `func_door` unlocks or opens / closes, `monster_*` appear (`hide`) or wake up (`trigger`), entities with a `hide` key show / hide (`TD3BrushEntity.SetHidden`, `Scene.Exists`, so they don't collide either), `func_remove` hides its targets for good. Other classes are logged once (`Not supported yet: activating <class>`), as are `call` keys (script functions).
- Trigger volumes: brush triggers have no render geometry (their material is `trigger`, not drawn), only a `.cm` model named like the entity, in entity-local coordinates: `SpawnTrigger` places its vertices at the origin (rotated) and takes their box. The player's box (feet to eye + 6, radius 16) touching it fires `trigger_once` (then disabled) and `trigger_multiple` (again after `wait`); `trigger_hurt` damages every `delay` seconds by the `damage` of its `def_damage` entityDef.

## Movers

- `TDoom3Map.Rebuild` merges each entity's entityDef (`classname`, `inherit` chains) into its keys first, skipping `editor_*`: the map's keys win, like Doom 3's spawn args. So `func_door` gets its def's speed, `triggersize`, sounds, `func_rotating` its `start_on`.
- `func_door` (`TD3Mover`, `mkDoor`): like `idDoor`, it travels the size of its *world* bounds along `movedir` minus `lip` (most retail doors are rotated), and opens when the player's eye enters those bounds grown by `triggersize` (default 60). Doors with the same `team` open, close and lock together (`TD3Game.OpenTeam` / `CloseTeam` / `LockTeam`). A door's area portals are closed while it is shut.
- `target_lock` locks (`locked` 1) or unlocks (0) its target doors and their teams. Activating a locked door unlocks it.
- `func_rotating` (`mkRotating`) turns while `Running` (`start_on`); activation stops / starts it.
- `bind`: brush entities and static / md5 models named by another entity's `bind` follow it (`TD3Binding`: the child's transform relative to the parent's at spawn, reapplied with `MatrixDecompose` when the parent moved). Bound lights and binding to md5 joints (`bindToJoint`) are not done; `func_mover` / `func_elevator` paths come with scripts (roadmap 5c).

## Scripts

- `TD3Game.StartScripts` (end of `Spawn`) compiles `script/doom_main.script` (it `#include`s the game's other scripts, map scripts included) and then `maps/<map>.script` into one `TD3ScriptVM`, like idProgram. A compile error turns scripts off for the map (logged). Then, like idWorldspawn, the map script's global `main` and worldspawn's `call` keys start on the first frame; triggers' `call` keys start when they fire their targets (idTrigger::CallScript).
- The compiler follows idCompiler: types `void float boolean vector string entity` and `object` types (fields and methods, called virtually by name), namespaces (`a::b`), globals with constant initializers, `scriptEvent` declarations of engine events, `$name` entities, `'x y z'` vectors and their `name_x` components, `thread f()`, `int()`. Priorities differ from C: `& |` bind like `*`, assignments bind tighter than `&& ||`, and `&& ||` evaluate both sides. `#define`s (with parameters too) stay defined for the files compiled later.
- The VM is a stack machine with one value stack and call stack per thread, so a thread can stop in the middle of nested calls: `sys.wait` (game time), `waitFrame`, `waitFor` (until `TD3ScriptHost.EntityBusy` is false: a script mover or a door still moving), `waitForThread`. `thread f()` runs the new thread at once until it waits. A thread running a million instructions in one frame is stopped (runaway loop). Events the VM handles itself (waiting, threads, printing, math, strings) work on any target; the others go to `TD3GameScriptHost` → `TD3Game.ScriptEvent`; unknown ones are logged once (`Not supported yet: event "x"`) and return their type's default.
- Entity handles are indexes in the map's entity list + 1 (0 is `$null_entity`).
- `TD3ScriptMover` (created on an entity's first mover event) keeps Doom 3 origin and angles, relative to the master when the entity is bound (then the script moves change `TD3Binding.ChildInParent`), and interpolates `move` / `moveTo` / `moveToPos` (over `time`, or distance / `speed`) and `rotateOnce` / `rotateTo` (over `time`) with idMover's acceleration and deceleration times; `rotate` turns until `stopRotating`. Bindings are updated parents first, so chains of bound machine parts follow in the same frame.
- `setGuiParm` sets the entity's key (`gui_parm1`...) and redraws its GUI screens: `TDoom3Map.SetGuiParm` finds the `d3gui:` textures of the entity's scene, gets each one's GUI file back from the GUI cache (`GuiUrlPath`) and points the texture at the GUI drawn with the new state (drawn once per state, then cached).
- `startSpline` moves a script mover along the `curve_*` key of a `func_splinemover` (control points in map coordinates, evaluated as a clamped uniform cubic B-spline like idCurve_NURBS with equal weights) over `time` (or the curve's length / `speed`), turning it with the curve's direction from the angles it had.
- Sounds from scripts (`startSoundShader`, `startSound` with a `snd_` key, `stopSound`) play on a `TCastleSoundSource` behavior of the entity's scene (or of a transform at its origin); a sound on a channel other than 0 replaces the channel's previous one.
- Not done yet: script objects on entities (monsters' and weapons' AI, roadmap 5d), `setColor` / `setShaderParm` on brush entities and models (their materials' parms), bound lights.

## Cinematics

- Activating an entity whose entityDef has `spawnclass` `idCameraAnim` (for example `marscity_cinematic_cam`) loads the file of its `anim` (the def's `anim <name>` key, `x.camera` meaning `x.md5camera`) into a `TD3CameraAnim` (cached) and makes it the view: `TD3Game.CinematicView` samples it at the time since the start, plus `origin - old_origin`. Like idCameraAnim, playback skips one frame at each cut and doesn't blend into the next shot; the frame's quaternion turns the camera's +X (forward) and +Z (up) like md5 joints (checked: Mars City's first camera looks at its console screen 17 units away, like in dhewm3). At the end (after `cycle` loops) the camera fires its targets, usually the next shot. `idCameraView` (`func_cameraview`) shows the view from the entity (or towards `cameraTarget`).
- `TViewPlay.UpdateCinematic` moves the camera there, sets the horizontal field of view, hides the HUD and stops the walk navigation; the player stays where they were (triggers keep using that position). _Escape_ (console `skipcinematic`) stops the camera and, for a second, every camera started after it, so a chain of shots is skipped.
- `trigger_fade` (`idTrigger_Fade`) and `sys.fadeIn` / `fadeOut` / `fadeTo` fade `TD3Game.FadeColor` (RGBA) from its current value; the view draws it with the `FadeRect` control of the design. `info_player_teleport` (`idPlayerStart`) sets a teleport that the view applies (after the cinematic).
- Lights fade with `TD3LightInfo.Fade` (a scale of the light's color, `TDoom3Map.SetLightFade`): `fadeOutLight` / `fadeInLight` change it over time (an off light comes on dark first).
- `idAnimated` md5 entities (`TD3Animated`): at spawn they show the first frame of `anim` (`TD3Md5Instance.SetFrame`, paused) or loop `start_anim`; `wait` activates them after that many seconds. Activation shows them and plays `anim` (`cycle` times, -1 forever) or the next of `anim1`..`anim<num_anims>`; at the end of each anim (`AnimLength` x cycles) they fire their targets, then are removed (`remove`), play the next anim (`auto_advance`) or can be activated again.
- Cinematic characters (`cinematic` `1`, idAI in Doom 3): activation shows them and plays their `anim` once, holding its last frame; their head plays its own anim of the same name (lip sync). Their AI script and `path_anim` paths are roadmap 5d.
- Heads (`def_head`, a model decl, at the body's `head_joint`; `TDoom3Map.BuildHead`): a second `TD3Md5Instance` in a transform under the body's holder, moved every frame to the joint, turned by the joint's rotation since its bind pose (`JointTransform`: head meshes are upright for the bind pose, so the joint's own bind orientation must not turn them). The map log line counts them (`(N with heads)`).
- Not done yet: screen GUIs changing during the cinematic (GUI scripts, item 4); shadows of the big moving models (the hangar's ship and doors) make some hangar shots dark.

## Actors (AI scripts)

- `TD3Game.SpawnActors` (after the scripts compiled) makes a `TD3Actor` for each idAI md5 entity whose `scriptobject` is a `character` (or derives from it), except monsters (they keep the game's simple AI for now) and cinematic characters (they play their `anim` when activated). The actor owns a `TD3ScriptObject` of that type (`TD3GameScriptHost.EntityObject` gives it to the VM: `self`'s fields, methods by name).
- Like idActor, the main thread runs the object's `init`, then state functions: `setState` / `setNextState` choose the next one, which `UpdateActors` starts in the main thread on the next frame (`TD3ScriptVM.RestartThread`; `setState` also stops the current thread now with `Yield`). Each animation channel (torso, legs, head, eyelids; `ANIMCHANNEL_ALL` means the legs) has its own thread for `animState` functions (`Legs_Idle`, `Legs_Walk`...). These threads are `Persistent`: the VM keeps them when their function ends.
- Animations: torso and legs play on the body's md5 instance (the last call wins), the head channel on the head. `animDone` compares the time since `playAnim` with the anim's length minus the blend frames (24 per second); cycles are never done.
- Movement: `moveToEntity` / `moveToPosition` walk straight to the goal (no AAS paths, no collisions yet) at the walk animation's speed (`TD3Md5Instance.AnimSpeed`, its origin joint's speed; the instance's `LockOrigin` keeps the mesh on the entity meanwhile), turning towards it; `turnTo` turns at `turn_rate`. Each frame the actor writes `AI_FORWARD`, `AI_MOVE_DONE`, `AI_ONGROUND`, `AI_DEST_UNREACHABLE` into its object; activation sets `AI_ACTIVATED`.
- `waitAction` makes the thread wait (`TD3ScriptThread.WaitFor` the actor) until `finishAction`; `callFunction` / `hasFunction` (in the VM) call the object's method by name in the current thread, which is how characters run their path commands (`callFunction( "path_corner" )`).
- Monsters whose script object is in `ScriptedMonsterObjects` (`monster_zombie`, and `monster_test` of the test level) are actors too; they keep their `TD3Monster` for health and shots (its simple AI off: `TD3Monster.Actor`). The player is their only enemy, with a handle of its own for scripts (`PlayerHandle`: `getOrigin`, `getName`, `getHealth`): `checkForEnemy` / `findEnemy` see it within `MonsterSightRange` (and a 180 degree field of view), `moveToEnemy` chases it (the goal follows it, done within `melee_range`; monsters move with `StepTowards`, the collision and floor following of the simple AI), `AI_ENEMY_VISIBLE` / `AI_ENEMY_IN_FOV` / `AI_ENEMY_DEAD` are kept up to date. A shot sets `AI_PAIN` for a frame and makes the player the enemy; a deadly one sets `AI_DEAD` and starts `state_Killed` (the zombies then `stopThinking`; the body sinks like the simple AI's).
- Animations: torso and legs channels play on one body, so each frame the body plays the torso's action (a `playAnim` not done yet), else the legs' anim, else the torso's idle. Names resolve like idDeclModelDef: `idle` is one of `idle1`..`idle3` at random (`ResolveAnim`), chosen when the script asks (so `animDone` knows its length).
- Frame commands (`TD3ModelDecl.FrameCommands`, fired by `TD3Md5Instance.OnFrameCommand` as the anim passes their frame): `melee <damage def>` hurts the player when in reach (the def's `damage`), `sound*` plays the entity's `snd_` key.
- Projectiles (`TD3Projectile`): a `launch_missile <joint>` frame command fires `num_projectiles` of the monster's `def_projectile` from the joint (`TD3Md5Instance.JointPosition`) at the player's chest, at the def's speed (`velocity` x), on the lower arc that reaches the player when the def has `gravity`, turned randomly by `attack_accuracy` (the volley) and `projectile_spread` (each). `UpdateProjectiles` moves them each frame; one detonates on the world (a ray cast along its step), near the player (it hurts with its `def_damage`'s `damage`) or when its `fuse` ends, playing `snd_explode`. Projectiles with a `light_color` and `light_radius` (fireballs) are drawn as unlit spheres in that color (no particles or light yet, item 7).
- More attacks (idAI, for the full game's monsters): `create_missile <joint>` (frame command) / `createMissile` (event) puts a projectile in the monster's hand (`TD3Projectile.HeldBy`: it follows the joint, harmless) until `launch_missile` / `attackMissile` throws it (`TD3Game.LaunchMissile`, the held one first, like idAI::LaunchProjectile: Doom 3's sine wobble by `attack_accuracy` (default 7), the yaw clamped to `attack_cone` (default 70) of its facing, `projectile_spread` per projectile); `fire_missile_at_target <joint> <entity>` / `fireMissileAtTarget` aim at an entity without the cone; `launchMissile( origin, angles )` throws along given angles. `attack_begin <damage def>` / `attackBegin` / `chargeAttack` start a multiframe attack: the first frame the player is in melee reach (idAI::TestMelee) it takes the def's damage and the attack ends (idAI::DirectDamage); `attack_end` / `attackEnd`, `direct_damage`, `directDamage`, `attackMelee` (returns the hit), `meleeAttackToJoint` (a trace from the eyes to the joint), `radiusDamageFromJoint` (RadiusDamage from the joint), `testChargeAttack` (the distance, no path check), `canHitEnemyFromJoint`. Missile events return `$null_entity` (projectiles are no entities here).
- Projectiles like idProjectile: the speed is the length of `velocity`; `detonate_on_world` / `detonate_on_actor` (missing means 0) decide between exploding and bouncing (reflected about the surface's normal, keeping `bounce` of the speed; lying still on a floor); `idGuidedProjectile` (revenant rockets) turns towards the player's eyes minus 12 by up to `turn_max` degrees a second (per 1/60 s tick in Doom 3), wobbling by `random` within `clamp_dist`, with `burstMode` / `burstDist` / `burstVelocity`.
- `ScriptedMonsterObjects` also has `monster_demon_imp`, `monster_zombie_security_pistol` and `monster_zombie_bernie` (every scripted monster of the demo), and the full game's walking monsters (`monster_demon_hellknight`, `_mancubus`, `_revenant`, `_maggot`, `_pinky`, `_trite`, `_tick`, `_cherub`, `_wraith`, `_archvile`, `monster_zombie_commando`, `_commando_cgun`). Their scripts aren't in the demo, so they are unchecked: what they ask that isn't done (teleporting, summoning, leaps, throwing objects) answers no. The flying monsters (`monster_flying_cacodemon`, `monster_flying_lostsoul`) and the bosses (`monster_boss_cyberdemon`, `_guardian`, `_guardian_seeker`, `_sabaoth`, `_vagary`) are scripted too, as unchecked.
- Flying (idAI::FlyMove), after the script's `setMoveType( MOVETYPE_FLY )` (`TD3Actor.MoveType`; `MoveTypeDead` / `MoveTypeStatic` don't move): `TD3Game.UpdateFlying` keeps a velocity that seeks the goal (the enemy's feet when chasing, `fly_seek_scale` x), bobs (`fly_bob_strength`; idAI reads `fly_bob_vert` into the horizontal bob and `fly_bob_horz` into the vertical one), rises or sinks to the enemy's eyes plus `fly_offset` (up to the ceiling; not while flying to a position), is damped (15% a second) and eases towards `fly_speed` while moving or 0 when stopped, like idAI (Seek predicts 0.3 s ahead). Seeking the enemy's floor position (x4) outweighs the height (x1) while chasing, as in Doom 3: flyers hover high when their script stops or uses `moveToEnemyHeight`. `FlyStep` moves each axis that isn't blocked (no floor following). It faces where it flies and leans into turns (`fly_roll_*`, `fly_pitch_*`, eased 5% a tick; the whole model, also with `bone_flytilt`). `chargeAttack` flies straight at the enemy's eyes plus `fly_offset` at `fly_speed` (`MoveDirect`, MOVE_TO_POSITION_DIRECT) until it gets there or hits a wall. Killed, a flyer falls (gravity 1066) to the floor, then sinks.
- Flying routes (idAASLocal::FlyPathToGoal): a flyer moving to a goal in another AAS area heads for `TD3Game.FlyRouteWaypoint`: along its route (walk, air and fly reachabilities) the furthest reachability start or end it can fly straight to (`FlyPathClear`: its center line and both sides clear), the goal once it sees it; straight to the goal in the same area or without an AAS. The flyer's area is the one its origin is in (it's in the air), else the one below.
- Moveables (idMoveable: `spawnclass idMoveable`, `moveable_*`; their LWO / ASE or brush models): `TD3Moveable` gives the entity's scene simple rigid body physics without spin: at rest until moved (activation with `init_velocity`, `setLinearVelocity`, a throw, let go by its bind master), it falls (Doom 3's gravity, 1066), moves one axis at a time (rays from its center and near its side's corners, not hitting its own scene), bounces (`bouncyness`), slows on floors and rests. Moving against the player it hurts it once a second by `def_damage` scaled by its speed between `minDamageVelocity` and `maxDamageVelocity` (idMoveable::Collide) while its damage is on (off with `damageWhenActive` until `enableDamage`, which turns it on for 2.5 s), and bounces off. Events: `setLinearVelocity`, `getLinearVelocity`, `enableDamage`, `isAtRest`.
- Thrown objects: the vagary's `chooseObjectToThrow( mins, maxs, speed, minDist, offset )` (a moveable in the box around the monster, far enough from the enemy's eyes, not behind the monster, that it can reach on a lower arc at that speed: `BallisticDir`, PredictTrajectory without its collision checks) and `throwObjectAtEnemy( entity, speed )` (`ThrowMoveable`: that velocity, damage on for 2.5 s), for any scripted monster; `throwMoveable` lets go of a moveable bound to the monster.
- More idAI events: `setFlySpeed`, `setFlyOffset`, `clearFlyOffset`, `moveToEnemyHeight`, `waitMove` (the thread waits for the move), `slideTo` (a move), `moveOutOfRange`, `getEnemyPos`, `getEnemyEyePos`, `enemyPositionValid`, `findEnemyAI`, `getRandomTarget` (one of its targets of a class), `findActorsInBounds` (the player in the box), `travelDistance*` (straight lines), `canReach*`, `setHealth`, `kill`, `getTurnRate` / `setTurnRate`; `throwAF` / `becomeRagdoll` return `$null_entity` (no ragdolls); burning, particles, clip and gravity switches do nothing. What their scripts ask that the game doesn't do answers no: dodges (`testAnimMove`), leaps (`getJumpVelocity` is zero), combat nodes, cover. Movement events set `AI_MOVE_DONE` / `AI_FORWARD` at once, like idAI (scripts test them right after `moveToEnemy`).
- Debugging: console `near <entity> [distance]` puts the player in front of an entity, `activate <entity>` triggers it (hidden monsters show up and hunt).
- Talking (idAI::TalkTo): `TD3Game.Use` first looks for a character within 128 units in front of the player (32 off the line of sight) whose `TalkState` is `TALK_OK` (2, `setTalkState`); its `TalkTarget` becomes the player (`PlayerHandle`, also what `$player1` resolves to) and `AI_TALK` turns on at once. The script plays the head's lip sync anim on `ANIMCHANNEL_HEAD` (the head instance has the head decl's frame commands, so `sound_voice` speaks) and ends the talk with `setTalkTarget( $null_entity )`. `getHead` returns the actor itself when it has a head (the head is no entity here).
- Splash damage (idGameLocal::RadiusDamage): a projectile whose def has `def_splash_damage` hurts the player when it explodes within that def's `radius` of the player's box (32 x 32 x 74 on the feet), by `damage` * (1 - distance / radius), if a ray from just off the impact point to the player's center is clear; not after a direct hit (RadiusDamage ignores the entity hit). A projectile whose fuse ends vanishes, unless its def says `detonate_on_fuse` (then it explodes, with its splash). `TD3Game.SpawnProjectile` makes one from a def (the unit tests use it).
- Sight (`TD3Game.CanSee`, `checkForEnemy`, `canSee`...) is a ray cast on the pickable geometry, like Doom 3's MASK_OPAQUE trace: playerclip / monsterclip brushes of the `.cm` (which the player collides with) don't block it. Brush entities made only of `nonsolid` surfaces (heat haze sprites...) neither collide nor are pickable.
- Head looks (idAI::UpdateAnimationControllers): `lookAt( entity, duration )` / `lookAtEnemy( duration )` set the actor's focus (the player's eyes a little lower, an actor's eyes, an entity's origin). `TD3Game.UpdateLook` turns `LookAngles` (pitch, yaw relative to its facing) towards it, clamped to `look_min` / `look_max`, eased by `head_focus_rate` per 1/60 s, back to straight ahead without a focus; a focus lasts through the frame it ends in (scripts renew 0.1 s looks every frame, and frames here can be longer). Each `look_joint <joint>` gets `TD3Md5Instance.SetJointMod` with its share of the angles (`QuatFromAngles`, like JOINTMOD_WORLD: the joint and its subtree turn about the joint in model space, after the animation). The pose with mods (`TD3Md5Instance.Pose`) is what's skinned and what `JointTransform` / `JointPosition` read, so heads and attachments follow.
- `copy_joint <body joint>` = `<head joint>` on the body's def: the head model's joint takes the body joint's local rotation every frame (`AddCopyJoint`, JOINTMOD_LOCAL_OVERRIDE): its neck follows the body's animation and looks. `copy_joint_world` (the eyes) isn't done.
- AAS routes (idAI::PathToGoal): `TD3Game.Spawn` loads `maps/<map>.aas48` (the size of the player and most monsters; the demo has no other sizes). An actor moving to its goal (path corners, `moveToEnemy`) and the simple monster AI steer to `RouteWaypoint`: the end point of the next reachability of the cheapest path from the monster's area to the goal's (`WalkingTravelFlags`: walk, walk off ledge, air), passing points closer than 12 units; straight to the goal in the same area, without an AAS or without a route. The path is cached per (from area, to area). Plane distances in the file are `normal . p - dist` (`idPlane::SetDist`). Monsters open doors (any living monster inside a door's trigger box), so routes through doorways work. Console `aas [entity]`.
- Dodges and path anims (idAI's AnimMove): actors (monsters and characters) that aren't walking move by their animation's origin, like idAI with MOVETYPE_ANIM: the mesh's origin stays (`LockOrigin`) and the entity moves by `TD3Md5Instance.LastOriginDelta` (the origin joint's X / Y move in the last update, across a cycle's wrap), turned by its yaw, with `StepTowards`' collisions; each delta is used once. `testAnimMove( anim )` / `testAnimMoveTowardEnemy( anim )` (`TD3Game.AnimMoveClear`) check the anim's whole move (`AnimMovementDelta`, idAnimator::TotalMovementDelta) turned to the ideal yaw / towards the enemy: nothing in the way of its box and no ledge (a drop of more than a step) at the end; false without the anim. The origin's move starts at the anim's first frame (`PlayAnim` sets it), so a whole anim moves an actor by its whole delta. Characters use their `size` key for collisions (`ActorRadius` / `ActorHeight`: 32 x 72 by default), monsters their monster's box; a stopped thinker (`stopThinking`) plays its anims in place again.
- Combat nodes (idCombatNode: `ai_attackcone`, any entityDef with `spawnclass idCombatNode`): `TD3CombatNode` keeps the cone (`min` / `max` along its facing, `fov`, `height` around origin + `offset`); `PlayerInView` is idCombatNode::EntityInView for the player's box. `getCombatNode` returns the closest node among the monster's targets that has the player in its cone and is closer than the player; `findEnemyInCombatNodes` returns the player when one of them has it in view; `enemyInCombatCone( node, ... )`; `node.markUsed()` turns off `use_once` nodes; activating a node toggles it; `start_off`.
- Not done yet: projectile entities for scripts (the missile events return `$null_entity`), moveables spinning, pushed by shots and explosions or pushing each other, ragdolls (`throwAF`), teleporting and summoning, eye focus, other AAS sizes, jumps / ladders / elevators in routes, AAS navigation, pushing, cowering, ragdolls.

## Items and the inventory

- The inventory (idInventory) lives in `TD3Game`: `InitInventory` (from `Spawn`, like idInventory::RestoreInventory) reads the player's entityDef, `player_doommarine`, or the test level's `player_test` when there is none (the test PK4 is mounted first and the first definition wins, so test data uses its own names): `maxhealth`, `armor` (50 by default), `maxarmor`, the weapon slots `def_weapon0..15`, the starting `weapon` list and `ammo_*` counts. Ammo is by class name (`ammo_bullets`...), up to the def's `max_<class>` (none can be carried without one); `Clip[slot]` is -1 until a weapon is first used (then full, like Doom 3). The inventory isn't kept between maps yet.
- `Give( stat, value )` is idPlayer::Give / idInventory::Give: `health` (up to `MaxHealth`), `armor`, `ammo_*`, `inclip_<ammo class>` (sets the clip of the weapon whose `ammoType` it is), `weapon` (a comma-separated list of weapon entityDefs, by slot); it returns False when it took nothing (full), so the item stays. `stamina` adds up to 100, `berserk`, `mega`, `adrenaline` give powerups; `item`, `icon`, `name` are ignored, air and heart rate are taken without effect for now.
- Items (`TD3Item`): entities whose `spawnclass` is idItem, idMoveableItem, idItemPowerup, idPDAItem, idMoveablePDAItem or idVideoCDItem. Their model is a static model (`TD3BrushEntity`). The player (a 32 x 32 x 74 box on the feet) touches the item's box: `triggersize` around the origin when set, else the model's bounds (idMoveableItem: grown by `triggersize`, 16 by default). `PickupItem` (idItem::Pickup / idPlayer::GiveItem) gives every `inv_*` key, or for carried items (`inv_carry`, PDAs, video discs) adds `inv_name` to `Carried`; when anything was taken it hides the item, plays `snd_acquire`, shows `inv_name` (`#str_` names through `strings/english.lang`) and fires its targets. `triggerFirst` / `no_touch` items can't be touched until activated; activating an item otherwise picks it up. `spin` items turn and bob like idItem::Think. Moveable items don't fall yet.
- Weapons are entityDefs that are also their own pickup items (`weapon_shotgun`: `spawnclass idItem`, `inv_weapon weapon_shotgun`, `ammoType`, `clipSize`).

## Weapons

- The player's weapon (`TD3Weapon`, idWeapon) is made from the def in the selected slot by `SpawnWeapon` (idWeapon::GetWeaponDef): `ammoType`, `ammoRequired` (0: needs no ammo), `clipSize`, `def_projectile`, `def_melee` / `melee_distance`, the view model `model_view` (an md5 model decl) and the script object `scriptobject`. A first-used weapon's clip (`Clip[slot]` -1) is filled from the ammo; ammo counts include the clip, like Doom 3.
- Its script object runs in its own persistent thread (self is `WeaponHandle`): `init` first, then the state functions. `weaponState( name, blend )` yields; `UpdateWeapon` restarts the thread at the new state on the next frame (idWeapon::UpdateScript does it within the frame). Every frame `UpdateWeapon` sets `WEAPON_ATTACK` (the attack button held, `TD3Game.Attack`, or `AttackOnce` from a demo script, held until the weapon fires or a second passes) and `WEAPON_RELOAD` (one frame after `ReloadWeapon`).
- Switching (idPlayer::UpdateWeapon): `SelectWeapon` / `NextWeapon` set the ideal slot; a ready weapon gets `WEAPON_LOWERWEAPON`, its script plays `putaway` and calls `weaponHolstered`; then the new weapon is spawned with `WEAPON_RAISEWEAPON` (its `init` goes to `Raise`). A weapon without a script switches at once. The player def's `current_weapon` (1) is the first weapon.
- Events (`WeaponEvent`): `weaponState`, `weaponReady` / `weaponOutOfAmmo` / `weaponReloading` / `weaponHolstered` / `weaponRising` / `weaponLowering` (the status), `ammoInClip`, `ammoAvailable`, `totalAmmoCount`, `clipSize`, `useAmmo`, `addToClip`, `playAnim` / `playCycle` / `animDone` on the view model (blend frames are 1/60 s), `launchProjectiles`, `melee`, `getOwner`, `nextWeapon`, `autoReload`, key and sound events (`startSound` names a def key); the flashlight, brass, skins and light parameters do nothing yet; `createProjectile` and `getWorldModel` return `$null_entity`.
- `launchProjectiles( num, spread, fuseOffset, launchPower, dmgPower )` (idWeapon::Event_LaunchProjectiles): takes `ammoRequired` from the ammo and one from the clip, then spawns `num` projectiles of `def_projectile` from the eye, each in a random direction within `spread` degrees, at the def's speed times `launchPower`, its damage times `dmgPower`. The player's projectiles (`FromPlayer`) skip the player and hit the first living monster on their path that no wall hides (`RayMonster`: monsters as cylinders), splashing monsters too (`MonsterSplash`). `melee` casts the view ray `melee_distance` far: the nearest monster before a wall takes `def_melee`'s `damage`.
- The view model: an md5 instance under a holder at the eye, turned with `PlayerViewDir` (`PlayerViewAxis`, Doom 3's view axis), lit by the map's lights (its scene adds the light library), casting no shadows, hidden until its first anim and when holstered; its frame commands play `sound*` keys of the def. No bob, kick or depth hack yet (it can poke into walls).
- Presentation (`PresentWeapon`, after the scripts so a shot's flash shows in its own frame): `UpdatePlayerMotion` takes the player's velocity from the eye's moves (teleports ignored), runs the bob cycle (idPlayer::BobCycle: on the ground above 5 units a second, pm_walkbob 0.3 to pm_runbob 0.4) and logs movement changes in view space. The view model is placed like idPlayer::CalculateViewWeaponPos: bob angles from the cycle's sine and the speed, a speed sensitive idle drift, the lag behind turns (the view angles smoothed over `weaponAngleOffsetAverages` / 60 s, times `weaponAngleOffsetScale`, within `weaponAngleOffsetMax`), the lag behind moves (`weaponOffsetTime`, `weaponOffsetScale`), the view bob's height (up to 6). Then idWeapon::MuzzleRise: each shot pushes the kick's end by `muzzle_kick_time`, at most `muzzle_kick_maxtime` ahead; the gun moves back by `muzzle_kick_offset` and turns by `muzzle_kick_angles` times the time left over the max time. `D3MatMul` / `D3VecMat` are Doom 3's matrix products (rows are axes).
- The view model's holder has `RenderLayer := rlFront`: CGE draws it with depth range 0..0.1 and the world with 0.1..1, like Doom 3's `weaponDepthHack`, so it never pokes into walls (and isn't shadowed by world shadow volumes).
- The view's bob (`UpdatePlayerMotion`, idPlayer::BobCycle and GetViewPos): `ViewBobAngles` (pitch from the forward velocity times pm_runpitch 0.002 plus the bob's sine times pm_bobpitch 0.002 times the speed, at least 200; roll from the sideways velocity times pm_runroll 0.005 plus the bob, the other way on every other step) and `ViewBobOffset` (up to 6 units up, pm_bobup 0.005; a landing dips it by idPlayer::CrashLand's landChange, 8 to 32 by the falling speed squared / 10000, 150 ms down and 300 ms back; the weapon dips a quarter more). The view model sits at the bobbed eye with the bobbed axis (`BobbedViewAxis`). `TViewPlay` applies the bob to the camera only while rendering (`Render` before the viewport draws, `RenderOverChildren` restores it): walk navigation updates before the view and must see the plain eye. CGE's `HeadBobbing` is off.
- Steps and falls (`UpdatePlayerMotion`): the view sets `PlayerJumping` (walk navigation's `IsJumping`) and `PlayerFlying` (noclip). CGE's `GrowSpeed` is 1000, so the camera is up a step at once; a rise of 1 to 33 units in a frame while walking on the ground is a step up: `FStepUpDelta` (decayed by the time since the last one, plus this one, at most 32) lowers the view and fades within 0.2 s (idPlayer::BobCycle's stepUpDelta, STEPUP_TIME); its vertical speed is left out of the view's angles. A rise without walking (lifts) isn't a step. A descent faster than 40 units a second starts a fall at the eye's height; when it stops, `CrashLand` (idPlayer::CrashLand) takes the height: delta = 2 * 1066 * height / 10000 (the landing speed squared / 10000 under Doom 3's gravity, whatever CGE's falling speed); > 7 dips the view by 8, > 30 / 45 / 65 by 16 / 24 / 32 with `damage_softfall` / `damage_hardfall` / `damage_fatalfall` (their `damage` keys, else 10 / 25 / 1000) through `DamagePlayer` (armor, god). Descending lifts count as small falls (a dip, no damage). CGE's `FallingEffect` is off.
- Falling speed: CGE's walk navigation falls at `FallSpeedStart` times `MoveSpeed`, growing exponentially by `FallSpeedIncrease`. `TViewPlay.UpdateFallSpeed` sets `FallSpeedIncrease` to 1 and, every frame, `FallSpeedStart` to `TD3Game.FallSpeed` (1066 times the seconds fallen, at mid-frame; at least 120) divided by `MoveSpeed`, then resets navigation's `Falling` so the next frame reads it (navigation updates before the view, so its `Falling` tells whether it fell this frame).
- Damage feedback (`DamagePlayer(Amount, DamageDefName, Direction)`, idPlayer::Damage and idPlayerView::DamageImpulse): callers pass the damage def (melee, projectiles' `def_damage` / `def_splash_damage`, moveables, falls) and the force's direction. Hits closer than 0.15 s to the last make no new effects. `kick_time` (ms) and `kick_amplitude` set the kick: the direction in the player's yaw axes gives pitch (forward + up), yaw (side / 2) and roll (side); `ViewBobAngles` adds kick times the ms left squared times 0.0001 (g_kickAmplitude), within 70 degrees, so the camera and the view weapon kick. `blob_time` / `mtr_blob` / `blob_*` add a screen blob (8 at most, positions jittered by 32, sizes by 1/8 like Doom 3) that `ScreenBlobs` returns while it fades; the view gives the HUD its material's image (`d3img:` URL). Pain cries (idActor::Pain) by the health left, `pain_delay` (the player def, 0.5) apart; `snd_death`, `snd_hitArmor` (0.2 s apart), and `CrashLand` plays `snd_land_hard` and holds the cry. Double vision: `dv_time` (ms) pushes `FDvFinish`, at most 5 s ahead; `DoubleVisionShift` is idPlayerView::DoubleVision's shift (the ms left times 0.001, at most 0.5, times the sine of the root of the ms left times 0.5); `TViewPlay` has a screen effect (`CreateDoubleVision`: the frame stretched from the shift, opaque, mixed half and half with the frame stretched to the shift's other side) enabled only while the shift isn't 0. `ArmorPulse` (1 fading to 0 in 0.25 s after armor absorbed a hit) draws `armorViewEffect`'s image over the screen, or a generated blue vignette when the game has no such material (the test PK4 must not define it: the retail one would lose). Knockback: the def's `knockback` (20 when missing; none without a direction) adds 1000 * knockback / 200 units a second along the force, horizontally; `KnockbackMove` returns the frame's move, slowing it like idPhysics_Player::Friction (pm_friction 6, pm_stopspeed 100) in 1/60 s steps, and `TViewPlay.ApplyKnockback` moves the camera with `WorldMoveAllowed` (radius 16). The force's vertical part counts: down on the ground it's dropped; up over 10 units a second (idPhysics_Player::CheckGround) `KnockbackAirborne` turns on, `KnockbackMove` then moves without friction under gravity 1066 (exactly, per 1/60 s step) and lands when it's back at the height it took off from (`FKnockRise`; the log says `Knockback: thrown up N units`). Meanwhile the view turns walk navigation's `Gravity` off (it would pull the camera down too); when `WorldMoveAllowed` refuses or shortens the vertical move, `KnockbackBlocked` ends the rise (a ceiling: it falls from there) or lands (going down). God mode skips all of it.
- Stamina (`UpdateStamina`, idPlayer::AdjustSpeed): the view sets `PlayerRunning` (walk navigation's `Input_Run`) and `PlayerMoving` (its move keys) each frame and `WalkNavigation.RunMultiplier` to `RunMultiplier`: pm_walkspeed 140 and pm_runspeed 220 blended by `RunFraction` over walking. Running and moving drains `Stamina` by the seconds (not under adrenaline); `RunFraction` is 1 above `StaminaThreshold` (45) or without stamina (`StaminaMax` 0, worldspawn's `no_stamina`), else stamina / threshold; so with Doom 3's pm_stamina 24 running is never at full speed except with adrenaline (stamina 100). Not running it regains `StaminaRate` (0.75, x1.25 standing still) up to `StaminaMax` (more is lost, as in Doom 3). `StaminaPercent` feeds the HUD bar (-1: none).
- Crouching (`UpdateCrouch`, `CanStandUp`): the view sets `PlayerCrouchHeld` (walk navigation's `Input_Crouch`, the console's `crouch`, a demo `GO:... crouch`; CGE's own crouch is off with `CrouchHeight` 1) and calls `UpdateCrouch` before `Update`. Holding it crouches (not in noclip); letting go stands up only when five segments (the box's center and corners, 14 in) from 37 to 74 above the feet don't collide (idPhysics_Player::CheckDuck). `EyeHeight` eases to 32 / 68 (10 dead) by 0.87 per 1/60 s (`Power(0.87, dt * 60)`, snapping within 0.05); the view moves the camera by its change and sets `PreferredHeight` to it (so CGE's gravity neither falls nor grows), the walk speed to `CrouchSpeedScale` (80 / 140), `RunMultiplier` 1 and `JumpMaxHeight` 0 while crouched (otherwise the design's jump height over the current `PreferredHeight`). `PlayerFeet` (the eye minus `EyeHeight`) and `PlayerBodyHeight` (74, 38 crouched, 20 dead) are what the game measures the player by: items, triggers, melee reach, splash damage, projectiles, monsters' targets; the motion's velocity, falls and steps are measured on the feet, so the eye going down isn't a fall. Holding crouch isn't running for stamina (Doom 3's upmove < 0).
- The player's body (`SpawnPlayerModel`, `UpdatePlayerModel`): the player def's `model` decl as a `TD3Md5Instance` (`LockOrigin`, no collisions or picking) in the holder `PlayerModelHolder`, which exists only with `ThirdPerson` (console `pm_thirdPerson`) outside cinematics; at the feet, turned to the view's yaw, playing `run` (over 170 units a second), `walk` (over 20) or `idle`, crouched `crouch_walk` / `crouch`; dead it plays `death` once (not looping: it holds the last frame; log `Player body plays death`). It also shows dead with `ThirdPersonDeath` (pm_thirdPersonDeath): `ThirdPersonActive`, and `ThirdPersonView` then backs away 20 + 120 * min(1, dead time / 3) without clipping, at the plain view angles (the view drops the dead tilt). Weapons' world models (`SpawnWorldWeapon`): `model_world` (an md5 model decl) in `WorldHolder`, a child of the body's holder, placed every frame at the body's `joint_attach` joint (`JointTransform`, like a `def_head`), shown while the view weapon's holder exists and not dead (log `Weapon ... world model ... on joint ...`). `UpdateFlashSurfaces` shows / hides a weapon model's flash surfaces (stage `if` with parm4 = -FlashStart) for the view and the world model alike; in third person `UpdateWorldWeapon` (after `PresentWeapon`) moves the muzzle flash light to the world model's `flash` joint (`FlashPosition`: backed up from walls along the gun's +x, like the view model's), logging `Muzzle flash of <weapon>'s world model at ...` once per shot. Brass (`EjectBrass`, `UpdateBrass`, `TD3Brass`): `LaunchPlayerProjectiles` schedules a casing `ejectBrassDelay` later (`FBrassDue`, ejected after the body's update so the world model's joint is current), and the `ejectBrass` event ejects one at once; the def's `model` (a static model) starts at the world model's `eject` joint in third person, else the view model's (none: no brass), with 40 * (forward + left + up) of `PlayerViewAxis` plus the player's velocity and a random spin. Each frame it falls (gravity 1066) along a `WorldHit` ray (the world's distance and surface normal, also the projectiles'): a hit reflects the normal part times `bouncyness` and keeps 0.7 of the rest, plays `snd_bounce` over 60 units a second, and on a floor under 40 units a second it lies down (`Resting`, log `Brass lands at ...`); after `fuse` (3 by default) it goes, 32 at most. Articulated figures (`Doom3AF`): `Decls` indexes `af/*.af` (`dtAF`, `DeclBody`), `ArticulatedFigure(name)` parses and caches one (`ParseArticulatedFigure`: values are read generically, numbers, strings, `( x, y, z )` vectors and `name( args )` calls separated by commas, then the keys the port uses are picked out). Bodies keep their joint, origin, model kind and bounds (`Radius`: half the smallest size, half a bone's width) and `containedJoints` (`JointList`: `*joint` adds the subtree, `-` removes, plain names one joint; empty = the body's joint); constraints their kind, bodies, anchor (`position`, `anchor`, `anchor1`) and `LimitAngle` (a cone's angle, a pyramid's larger angle, a hinge limit's width). Ragdolls (`Doom3Ragdoll`, `TD3Ragdoll`): created by `TD3Game.CreateRagdoll` for a `ragdoll` key (the figure if it exists, else the skeleton). With a figure, AF vectors are evaluated in the bind pose (standing in for Doom 3's af_pose) and moved into the current pose by the body's joint (`FromBind`); every body center is a particle (its radius for the world), every ball / universal / hinge an anchor particle shared by both bodies, every body's points rigidly linked, and the two centers linked between the distance at the largest bend (rest bend plus the limit) and fully straight; fixed and slider link the centers rigidly, springs loosely. `WritePose` turns each body by its first anchor's arc plus the twist that brings its next anchor around, moves its contained joints about its center and lets other joints follow their parent. The ragdoll sets `TD3Md5Instance.PoseLocked`: animations keep running (time, frame commands, `AnimFinished`) without touching the pose, and joint mods are off. Monsters: `MonsterRagdoll` at death (`DamageMonster`, `KillActor`) pushes it 120 away from the player; `UpdateMonster` steps it instead of falling and sinking, and the corpse stays (holder and scene not pickable). The player's ragdoll (`StartRagdoll`, below) is a `TD3Ragdoll` too. The ragdoll (`StartRagdoll`): when the dead body shows and the player def has `ragdoll` (and `RagdollEnabled`, console `ragdoll`), each joint of its current pose becomes a particle (world space) with links: parent (fixed length), grandparent (0.6..1 of it: bends, doesn't stretch) and siblings (0.8..1.2). Start velocities: the player's, the last hit's direction (`FLastDamageDir`) times 150 and 60 backwards, both growing with the joint's height. Steps of 1/60 s: verlet with 0.99 damping and gravity, 8 passes over the links, then each particle's move is a `WorldHit` ray and a hit stops it there (velocity zeroed: no sliding). Settled after 0.5 s under 0.05 units a step (or 10 s). The pose back: each joint at its particle (`WorldToLocal`), turned by the shortest arc (`QuatFromTo`) from its first child's start direction to the current one (leaves turn with their parent), set with `TD3Md5Instance.SetPose` (which pauses the animation); the holder stays where the body fell. Crouching and standing up play `crouch_down` / `crouch_up` once (not looping) before the loops (`FBodyCrouched`, `FBodyTransition`); a body that isn't shown just follows the state. `PlayerSkinName` is `skin_invisibility` while invisible, else the def's `skin` plus `_berserk` under berserk (when that skin exists), else `skin`; `TD3Md5Instance.SetSkin` remaps the meshes' original shaders and swaps the shapes' appearances (meshes the first skin hid stay away), holding the old appearances (`KeepExistingBegin`) until the scene let go of them: freed while the scene still enumerates their textures, they crash CGE. `ThirdPersonView` is idPlayer::OffsetThirdPersonView: the pitch at most 45, the focus point 512 ahead, the camera 8 + height above the eye and `ThirdPersonRange` (80) back along the half pitch, pulled in front of walls by `WorldRayCast` (and up by up to 32 units under a low ceiling), looking at the focus point; `TViewPlay.ApplyViewBob` applies it only while rendering, so screenshot log lines show the eye. The view weapon's holder is invisible in third person. Powerups: `FPowerupEnd` per powerup (PowerupBerserk 0, PowerupInvisibility 1, PowerupMegaHealth 2, PowerupAdrenaline 3, idItemPowerup's `type`); `GivePowerUp` (time 0: the `powerup_<name>` def's `time`, else 30) plays the player def's sound; `UpdatePowerUps` ends them on time; death and `InitInventory` clear them. Berserk: `SpeedModifier` 1.7 (the view multiplies walk navigation's `MoveSpeed`), `SelectWeapon(0)`, `WeaponMelee` reaches twice as far and does 30 times the damage, player projectiles twice, `DamageMonster` 1.7 times everything (idPlayer::DamageFeedback passes BERSERK where PowerUpModifier expects a type: SPEED), and `DamagePlayerByMonster` (melee, monster projectiles and splash, the simple monsters) does nothing. Invisibility: `SetWeaponInvisible` makes the view model's lit shapes 65% transparent with a cold emissive (Doom 3 swaps its skin for a refracting one), the HUD rims the screen, `isInvisible` returns 1. Screen: `textures/decals/berserk` (its image, alpha fading over the last 10 s) or a generated red tint; the test PK4 must not define `powerup_*` or that material. The HUD (`TDoom3Hud`) draws the blobs on Doom 3's 640 x 480 screen and the tunnel vision: a generated vignette, dark red, strength (1 - health / 100) * 0.55 plus a 0.4 pulse fading over 0.4 s after each hit (`DamageAge` from `TD3Game.SinceDamage`). Dead, the view tilts (roll 40, pitch -15). `ViewBobEnabled` (console `pm_bob`) turns the view's bob off; projectiles aim along the plain view.
- Muzzle flash: a shot sets `FlashStart`; for `flashTime` the light (`flashColor`, `flashRadius`, 0 = none) is at the view model's `flash` joint, moved back to 8 units from a wall (idWeapon::UpdateFlashPosition); `TD3Game.MuzzleFlash` gives it to the view's `MuzzleFlash` point light (intensity 1; the built-in pistol keeps its own short flash). The view model's meshes whose material has a stage `if` condition (`TD3Material.StageCondition`, the first plain stage's) show only while it is true with parm4 = -`FlashStart` (Doom 3's SHADERPARM_TIMEOFFSET): `if ( ( time + parm4 ) * 12 ) < 1.0` shows a flash for 1/12 s. Elsewhere stage conditions are still ignored.
- Without a script object (or without scripts), the slot fires the built-in hitscan pistol (`TD3Game.Fire`: 14 damage every 0.35 s). The HUD shows `WeaponHudText` (the def's `inv_name`, clip / ammo left).

- Console: `inventory` (also logged as `Inventory:`), `give all`, `give weapons`, `give <weapon def>`, `give <stat> <amount>`. The log says `Picked up <entity> (<name>)`.

## Reverb

- dhewm3 plays the full game's `efxs/<map>.efx` (EAX reverb settings, made with Creative's tools; none in the demo data) with OpenAL EFX. Here `TViewPlay.LoadReverb` loads `EfxPathForMap(MapName)` after spawning, and every frame `UpdateReverb` chooses an effect for the camera like `idSoundWorldLocal::MixLoop`: the one named by the camera's portal area number (`"17"`), else by its location, else `"default"`; when none matches, the previous effect stays. A new effect is `Assign`ed to CGE's `SoundEngine.Reverb` (CGE change L, `doom3-port`): one auxiliary effect slot with an EAX reverb that every spatial sound sends to. dhewm3 sends all sounds, also the player's own (not spatial here).
- Conversions like dhewm3's `idEFXFile::ReadEffect`: millibels to gains (`10 ^ (mB / 2000)`, clamped to the EFX range), `"environment size"` to density (`size^3 / 16`), `"flags"` bit `0x20` to `DecayHFLimit`; `"environment"` (the EAX preset) has no EFX equivalent.
- Locations (`TD3Game.SpreadLocations`, like `idGameLocal::SpreadLocations`): each `info_location` (its `location` key, else its name; lowercase) takes its area and floods through the portals, except those of doors closed at spawn and of `info_locationSeparator`s; an `info_location` in an area an earlier one already reached is skipped ("overlaps"), and later floods overwrite earlier ones. `LocationAt` / `LocationOfArea` read them; the HUD doesn't show them yet.
- Console: `reverb` (the area, location, file and current effect), `s_useEAXReverb [0|1]`, `soundinfo` (whether the OpenAL device has EFX). The log says `Reverb: Found efxs/<map>.efx: N effects` or `Missing ...`, and `Reverb: Effect "<name>" (area N, location "...")` on every switch.

## Rendering notes

- Each area's solid surfaces are one `TCastleScene` and its `nonsolid`, translucent and blended surfaces another with `Collides := False`; each material is its own shape, so frustum culling and per-shape light lists stay effective (`MaxLightsPerShape` 32).
- Lights are `Global` in the `Lights` scene with `CastGlobalLights`, so they light every area, brush entity and md5 model.
- Brush entity, static model and md5 scenes are children of `TDoom3Map`. Static model entities are `TD3BrushEntity` items too, so `func_door` / `func_rotating` with LWO models move like brush ones; md5 scenes don't collide and aren't pickable (shots test monsters as cylinders).
- Textures are referenced by URL (`d3fs:/...`, `d3img:/...`), so CGE's texture cache shares them between shapes and scenes. X3D nodes are never shared between scenes.

## Performance

How to measure:

- Every map load logs `Profile: Map "...": <seconds> (<phase> <seconds>, ...; N file reads, N image programs)`: the build phases (`proc+map`, `world`, `collision`, `brushes`, `static models`, `md5 models`, `spawn`, `scripts`...) and the first five frames (`frame 2` is CGE preparing every scene: textures, shaders, VBOs). `Profile: Data` is the startup (PK4 indexes, decls).
- The sampling profiler: build with the linker map (`castle-engine compile --mode=release --compiler-option=-Xm`), run with the environment variable `CD3_SAMPLE=1` (samples the map load and its first frames) or use the console `sample start` / `sample stop` (e.g. `O:sample start,W:8,O:sample stop` in a demo script), then `python tools/resolve_samples.py` (exclusive and inclusive functions) and `python tools/sample_callers.py <name part>` (the stacks above a function). Stacks stop at system DLLs (no frame pointers there): `[ntdll.dll]` is mostly waiting (vsync, the driver).
- GPU: `tools/nsight_gputrace.ps1` runs an NVIDIA Nsight Graphics GPU Trace (needs the GPU performance counters allowed for all users in the NVIDIA Control Panel, or an elevated shell) and exports per-frame metrics (`BASE\GPUTRACE_FRAME.xls`: engine busy %, SM / L1 / L2 / DRAM / ROP throughput, draw count, PCIe bytes). The OpenGL instrumentation makes frames with many GL calls very slow under the trace (Mars City Underground 75 ms to 1 s per frame, the test map 9 ms), so read the busy cycles, not the frame time. First results (GTX 1660 Ti, clocks locked to base): Mars City Underground needs only ~4 to 7 ms of GPU work per frame, almost all pixel shading (the light volumes), vertex work negligible, memory / ROP / texture units nearly idle; the test map keeps the GPU 64 % busy within its short frames (SM 28 %). The GPU is not the limit in the demo maps; the CPU side (GL calls: per-light uniforms on ~900 draws a frame) is where the time goes. GPU Trace splits time by debug markers (`glPushDebugGroup`), which neither CGE nor this port emits yet.
- `CD3_CGE_PROFILE=1` turns on CGE's `Profiler` (image loads, scene preparation) and logs its summary after the first frames.

What was slow and how it's avoided (Mars City Underground went from 46 s to 25 s from start to the first frames, gameplay from ~40 FPS to vsync):

- CGE prepares shadow volume edges for every scene when the viewport uses shadow volumes, even scenes that don't cast, by comparing each edge with every open edge so far (quadratic): seconds for the big open area meshes. `TD3Scene` drops `prShadowVolume` when `CastShadows` is off, and brush entities / static models whose surfaces are all open (`TrianglesClosed`) don't cast at all (CGE skips open shapes when casting anyway).
- GUIs are painted at 512 x 512 (a power of two; CGE resized every 640 x 480 GUI texture, bilinearly) with integer blending and pointer access, and GUI background images are loaded once (`GuiSourceImage`).
- PK4 entries are inflated from the memory mapped file, with the C zlib on Windows (CGE's `TZStream` is 4 bytes short on Win64, so `TPaddedZStream` pads it).
- md5 models are skinned only when portal visibility shows them (`TD3Md5Instance.Shown`; animations, frame commands and joints go on), with one 3 x 4 matrix per joint, straight into the coordinate node's list.
- Image programs (`heightmap`, `addnormals`) use integer heights, row pointers and no per-pixel `mod` or `Round`. Don't make `StoreNormal` `inline`: FPC 3.2.2 miscompiled it (speckled normal maps).

## The test level
